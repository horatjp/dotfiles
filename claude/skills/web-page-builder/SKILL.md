# WEBサイト作成スキル

静的なWEBサイト（LP・コーポレート・ポートフォリオ・イベント・ドキュメント等）をHTML/CSSで作りきるためのワークフロー。

思想は「AIを賢くするのではなく、AIが迷えない環境を作る」。デザインの正解を先に1枚の仕様（DESIGN.md）としてコードと同じ場所に置き、生成後は禁止パターンで自己検証する。

## スコープ

- 対象: 新規の静的サイト・LP・モックアップ。単一HTML（CSS/JS込み）を基本とし、要望があれば複数ページ・ファイル分割
- 対象外: 既存サイトのリニューアル案（→ site-renewal-design）、バックエンド/DBを伴うシステム

## ワークフロー

### Step 0: ブリーフを読む（Design Read）

コードやデザインに手を付ける前に、依頼を1行で解釈して宣言する。

**読む信号**: ①サイト種別（LP/コーポレート/ポートフォリオ/イベント/ドキュメント） ②ユーザーが使った雰囲気語（「ミニマル」「高級感」「ポップ」「信頼感」等） ③参照物（URL・スクリーンショット・競合名） ④オーディエンス（誰が見るか。審美眼のある消費者か、B2Bの決裁者か） ⑤既存ブランド資産（ロゴ・色・書体） ⑥暗黙の制約（公共・規制業種・アクセシビリティ重視・子供向け — これらは美的好みに優先する）

**宣言形式**:「〈オーディエンス〉向けの〈サイト種別〉として読んだ。〈雰囲気〉の言語で、〈方向性〉に寄せる。」

曖昧で方向が本当に分かれる場合のみ、**質問は1つだけ**する（AskUserQuestionがあれば使う）。推論できるなら聞かずに宣言して進む。ブリーフに実コンテンツがなければ、具体的な主題・ページの単一の役割を自分で決めて明示する。

### Step 1: DESIGN.md（デザイン仕様1枚）を作る

サイト本体より先に、出力先フォルダに `DESIGN.md` を書く。これがAI向けの「翻訳メモ」であり、以降の全判断のSSOT。構成:

1. **Overview** — 主題・オーディエンス・視覚的方向性を3行以内
2. **Color Palette** — 名前付きhexを4〜6色、表形式（トークン名 / 値 / 用途）
3. **Typography** — 役割別に2書体以上（個性ある見出し用+読みやすい本文用。必要ならデータ/キャプション用）、タイプスケール表（サイズ/ウェイト/行高/letter-spacing）
4. **Spacing & Layout** — 8px基準のスペーシングトークン、最大コンテンツ幅、レイアウト概念を1文+必要ならASCIIワイヤーフレーム。**骨格はロールで決める（収束防止）**: Claudeは放っておくと毎回同じ骨格（固定ヘッダー→2カラムヒーロー→数値帯→カード3列→CTA帯）に収束する。`python <スキルのパス>/scripts/roll_layout.py --count 1` で骨格+ヒーロー型+制約カードを抽選し、出目を題材に合わせて変形する。**接続テスト**: 「この骨格がこの主題とどう繋がるか」を1文で書けた出目だけ採用、書けなければ理由を1行残して振り直す（スクリプトが使えない環境では `references/layout-skeletons.md` から「最初に思いついたもの以外」を意識的に選ぶ）
5. **Signature** — このページが記憶される固有の要素を**1つ**決める（ヒーローの見せ方・独自の構造装置・モーションの瞬間など）
6. **Components / Motion / Breakpoints** — 使う部品と状態、トランジション方針（150〜300ms基準）、ブレークポイント

日本語サイトの場合は `references/japanese-web.md` のデフォルト（フォントスタック・行高・禁則処理・文化的UX）を必ず反映する。

### Step 2: 自己批評（テンプレ照合）

書いたDESIGN.mdをブリーフと照らし、次を確認してから実装に進む:

- 同種の依頼を受けたら同じ案を出しそうな部分はないか（あれば、その部分だけ作り直し、何をなぜ変えたか言う）
- AI生成デザインの定番3種（①クリーム背景+セリフ+テラコッタ ②漆黒+アシッドグリーン単色アクセント ③新聞風細罫線・高密度）に無自覚に落ちていないか。ブリーフが明示的に求める場合だけ許可
- 大胆さがシグネチャー1箇所に集中し、周囲は静かに規律が保たれているか

### Step 3: 実装

DESIGN.mdに正確に従ってコードを書く。色・書体・余白の値はすべてDESIGN.mdのトークンから引く（直書きしない）。

- セマンティックHTML（header/nav/main/section/footer）、見出し階層を正しく（h1は1つ）
- CSSカスタムプロパティ（`:root`）でトークンを定義してから使う。修正・反復時もトークンを起点に直す（場当たりの個別上書きは統一感を壊す）
- レスポンシブ必須: `<meta name="viewport">`、rem/em/%基準、`clamp()` での流体タイポ、モバイルまで確認
- 品質フロア（黙って満たす）: キーボードフォーカス可視、`prefers-reduced-motion` 対応、コントラストAA、alt/ARIA、タップ対象44px以上。数値基準（ジャンプ率・字間・余白スケール・dvh・text-wrap等）は `references/design-rules.md` の「仕上げ品質」節に従う
- **トップページは玄関として作る（無自覚なLP化の禁止）**: コーポレート・店舗サイトのトップを縦長の説得型LP（訴求セクション積み重ね+CTA連打）にしない。ナビは下層ページを指す（想定パス明記）、お知らせ等の更新枠（日付つき2-3件、ダミーなら明記）、一覧系はピックアップ+「一覧を見る」導線、フッターにサイトマップ、CTAは主導線1つ+補助に絞る。単品訴求・キャンペーン・イベント等LPが正解の題材は、その選択を宣言した上でLPとして作ってよい
- **スタイリング手段**: Tailwind Play CDN は表示環境が外部スクリプトを制限していると無スタイルで表示される事故がある。表示環境に確信が持てなければ `<style>` タグ内の素のCSSで書く。素のCSSではセレクタの詳細度競合に注意（.section と要素セレクタの打ち消し合いでpadding/marginが壊れやすい。セクション間余白は共通クラスに寄せる）
- **画像**: 自分でSVG/CSSイラストや疑似ビジュアルを描かない（品質がサイトを毀損する）。素材の優先順位・FPO（写真プレースホルダー）の作法・直リンクの実装形は `references/images.md` に従う
- UIコピーも設計素材: 能動態・ユーザー視点の命名（「変更を保存」であって「送信」ではない）、具体で言い切る（「創業40年、〇〇市の防水工事専門店」>「確かな技術で未来を創る」）。実在の事柄を捏造しない（創業年数・受賞歴・顧客名・数値実績を勝手に作らない。ダミーが必要な箇所は汎用的に留めダミーと明記）

### Step 4: 生成後の自己検証

実装が終わったら `references/design-rules.md` の禁止パターン一覧・最終プリフライトチェックと照合し、違反を修正してから納品する。

- コントラストは目視でなく `python <スキルのパス>/scripts/check_contrast.py "#文字色,#背景色" ...` で機械的に確認する（本文AA 4.5:1未満のペアは使わない）
- **スクリーンショット検証を必ず試みる**: PC幅（1440px）とモバイル幅（375px）の2枚をfull-pageで撮り、目視確認する。手段（PlaywrightヘッドレスChromiumのセットアップ・依存ライブラリの復旧・フォールバック）と確認観点は `references/screenshot-verify.md`。撮れない環境ではコードレビュー+コントラストスクリプトで代替し、「実表示は未確認」と明示する。修正したら撮り直す
- チェックの要点: 禁止色（純黒等）、常套骨格の再演、無自覚なLP化、3枚等幅カード、汎用ダミーデータ、ネオングロー、過剰アニメ、フォーカス/コントラスト

### Step 5: 納品とフィードバックのルール化

- 納品物: HTMLファイル一式 + DESIGN.md。ファイル構成と設計判断を簡潔に説明する
- ユーザーが出力を修正・指摘したら、その内容を `❌禁止 → ✅代替（理由）` の1行にしてDESIGN.mdの末尾（Rulesセクション）に追記することを提案する。**ルール化するかの判断は必ずユーザーの承認を挟む**。次回以降の生成はこのルールを読む

## 参照画像（スクリーンショット）からの作成

ユーザーが「この画像みたいに」と参照画像を出した場合:

1. **観察**: レイアウト構造（grid/flex）、コンポーネント種別、色（hexを正確に抽出）、書体の特徴、余白・影・角丸、レスポンシブの手がかり
2. **書体の同定（スキル自身で決める。ユーザーに確認させない）**: 書体は再現度の印象を最も左右するのに、最も外しやすい。1発で当てようとせず、自分で検証してから決める:
   - 観察の観点: 字幅（コンデンス/標準/ワイド）、ウェイト、角の処理（角ばる/丸い）、数字の形（0・3・6）、特徴的なグリフ（R の脚・G のヒゲ・S の絞り）、セリフ有無
   - 観察から候補を2〜3に絞り、参照画像と同じ見出し文言を候補書体で並べた比較HTMLを一時ファイルとして作り、**自分でスクリーンショットを撮って参照画像と突き合わせ**（`references/screenshot-verify.md` の手段）、グリフ単位で最も近い1つを**自分で決定する**
   - レンダリング手段がない環境でも、グリフ観察に基づき最も近い候補を自分で決めて進める。どちらの場合もユーザーへの質問はしない
   - 決定と根拠（どのグリフ・字幅が一致したか）をDESIGN.mdに1行記録し、納品時に「見出しは◯◯と判定」と結果だけ伝える。ユーザーから違うと指摘されたときのみ代替候補を提示する
   - 元書体が有料フォントらしい場合（Helvetica Condensed系等）はGoogle Fontsの最近似を選び、「近似である」ことを明記する
3. **忠実再現が目的**ならDESIGN.mdは観察結果から逆算して作り、比率・色を厳密に一致させる。**参考程度**なら雰囲気だけ取り込みStep 0からの通常フローに乗せる（どちらかは依頼文から判断し、宣言する）
4. 技術スタック未指定ならプレーンHTML/CSSをデフォルトにする
5. **権利物の丸写しはしない**: 実在の他社サイト・有料テンプレートのピクセル単位の複製依頼は断る（DNA=骨格・書体の性格・明度帯・アクセントの使い方を言語化して参考にするのは可）。ユーザー自身が権利を持つデザインの再現は問題ない

## デザイン原則（迷ったときの判断基準）

- **コンテンツが主役**: 装飾を足すか迷ったら「それはコンテンツの理解を助けるか？」で判断する
- **ヒーローはテーゼ**: 主題の世界で最も特徴的なものを開幕に置く。「大きい数字+小さいラベル+グラデアクセント」はテンプレの答え
- **タイポグラフィがページの人格を担う**: どの案件でも使う書体の組み合わせに逃げない
- **構造は情報**: 番号（01/02/03）・罫線・ラベルは内容が実際に順序や区分を持つときだけ使う
- **モーションは1つのオーケストレーションされた瞬間 > 散らばった効果**。少ない方が良いことも多い
- **複雑さはビジョンに合わせる**: ミニマル路線なら余白・字間・細部の精度で勝負する
- **色だけで情報を伝えない**（色覚多様性）。アイコン・テキストを併用する

## 複数案を求められた場合

「何案か見たい」と言われたら、案ごとに `roll_layout.py --count 案数` でロールし、**分離ルール**を守る: 隣り合う案どうしは骨格が異なり、かつ「紙の明度帯（明/中/暗）」「見出し書体の性格」「アクセント色相（暖/寒/無彩）」の3軸のうち2軸以上で異なること（「配色だけ替えた複数案」を防ぐ）。各案には内容から固有の名前を付け（×「ミニマル案」→ ○ 主題に根ざした名前）、戦略1行・トレードオフを添えて比較できる形で提示する。選ばれた案の深掘りは元ファイルを上書きせず `-v2` を付けて保存する。
