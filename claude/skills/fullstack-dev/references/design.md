# 設計ガイド(DB → API)

必ずDB設計を先に固める。APIはデータ構造の写像であり、逆順で進めると作り直しになる。

## DB設計

### 手順

1. 要件からエンティティを列挙する(名詞を拾う: ユーザー、予約、商品…)
2. エンティティ間のリレーションを決める(1:N / N:M / 1:1)
3. 各エンティティの属性と制約を決める
4. `docs/schema.md` に記述し、実スキーマ(Prisma schema / DDL)に落とす

### 規約

- **主キー**: `id`(cuid または UUID)。連番は外部に漏れると件数を推測されるため避ける
- **タイムスタンプ**: 全テーブルに `createdAt` / `updatedAt`
- **論理削除**: 要件にない限り使わない。必要なら `deletedAt`(nullable)方式
- **enum**: 状態は文字列enumで(`status: DRAFT | PUBLISHED | ARCHIVED`)。真偽値の乱立で状態管理しない
- **N:M**: 中間テーブルに意味がある名前を付ける(`ProjectMember`。`ProjectUser` のような機械的命名は避け、属性を持てる余地を残す)
- **金額**: 浮動小数点は使わない。整数(最小通貨単位)で持つ

### schema.md の書式

```markdown
## User
| フィールド | 型 | 制約 | 説明 |
|---|---|---|---|
| id | String | PK, cuid | |
| email | String | unique | ログインID |
| role | Enum | ADMIN / MEMBER | |

リレーション: User 1—N Reservation
```

## API設計

### 規約

- RESTを基本にする。リソース名は複数形(`/api/reservations`)
- ネストは1段まで(`/api/projects/:id/members` はOK、それ以上はクエリパラメータで)
- 認可はエンドポイント単位で明記する(誰が呼べるか)
- レスポンスは一貫した形にする:

```json
// 成功
{ "data": { ... } }
// 失敗
{ "error": { "code": "VALIDATION_ERROR", "message": "...", "details": [ ... ] } }
```

- 一覧系は必ずページネーションを付ける(`?page=` / `?cursor=`)。「後で付ける」は破壊的変更になる

### api.md の書式

```markdown
## POST /api/reservations
- 認可: ログインユーザー
- リクエスト: { roomId: string, startsAt: ISO8601, endsAt: ISO8601 }
- レスポンス: 201 { data: Reservation }
- エラー: 409 RESERVATION_CONFLICT(時間帯重複)
```

ビジネスルール由来のエラー(重複、在庫切れ等)はここで洗い出しておく。
実装中に発見すると設計もテストも後追い修正になる。

## RBAC設計(ロール分離がある場合のみ)

管理者/一般のようなロール分離が要件にある場合は、`docs/rbac.md` にロール × 操作のマトリクスを書く。
単一ロールのシステムなら rbac.md は作らない — 不要な構造は保守コストにしかならない。
作る場合、この表がAPI設計と画面設計の両方を貫く一枚になる。

```markdown
| 操作 | ADMIN | USER | 備考 |
|---|---|---|---|
| 商品一覧の閲覧 | ✓ | ✓ | |
| 商品の追加・編集・削除 | ✓ | — | |
| 在庫数の増減 | ✓ | ✓ | USERは自店舗分のみ |
| ユーザー管理 | ✓ | — | 自分自身の降格は不可 |
```

- 「✓/—」で書けない条件付き認可(自分のデータのみ等)は備考に明記する。
  実装時の認可チェックとテストケースはこの表から機械的に導出できる
- ロールが3つ以上になる場合も、まず表にしてから実装する。表にできない認可要件は
  要件自体が曖昧なので、要件整理に差し戻す

## 設計レビュー

エンティティ4個以上、またはN:Mリレーションを含む場合は、実装前にユーザーへ
schema.md / api.md を提示して合意を取る。小規模ならスキップ可。
