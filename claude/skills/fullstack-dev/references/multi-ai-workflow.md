# 複数AI協働ワークフロー(指示者 / 実装者の分離)

このスキルのプロジェクトは、1つのAIが全部やるのではなく、役割を分けた複数のAI
(セッション・ツールが違ってもよい)で進める。分ける理由:

- 設計判断とコード生成では最適なコンテキストの持ち方が違う。実装の詳細で頭が
  いっぱいのまま設計判断をすると近視眼的になる
- 実装者が自分の書いたコードを自分でレビューすると欠陥を見逃す
- コンテキストウィンドウは有限。役割ごとに読むファイルを絞ることで大きな
  プロジェクトでも品質が保てる

## 役割定義

### 指示者(Director)

- 担当: 要件整理、スタック選定、設計(schema/api)、タスク切り出し、成果物レビュー、判断の記録
- 読むもの: knowledge/ 全体、docs/ 全体。コードは差分・レビュー対象のみ
- 書くもの: docs/、knowledge/decisions/、tasks/(下記)
- **コードを書かない。** 書きたくなったらタスク指示書に落とす

### 実装者(Implementer)

- 担当: タスク指示書に従った実装、テスト作成、動作確認、詰まった点の記録
- 読むもの: 自分のタスク指示書、knowledge/mistakes.md、docs/ の関連部分、参照実装
- 書くもの: コード、テスト、knowledge/research/(ハマった問題)、完了報告
- **設計を勝手に変えない。** 設計の不備を見つけたら報告して指示者の判断を仰ぐ
  (緊急回避が必要な場合は変更内容を必ず記録して報告)

1人(1AI)で進める場合も、この2つの帽子を意識的にかぶり分ける。
設計フェーズと実装フェーズを同じ勢いで流さない。

## タスク指示書(指示者 → 実装者)

`tasks/` ディレクトリに1タスク1ファイルで置く。ファイル名: `NNN-短い題名.md`(連番)。
`tasks/` は指示者→実装者のタスク受け渡し専用。プロジェクトのISSUE管理とは混ぜない。

```markdown
---
status: todo   # todo | in-progress | done | blocked
depends: [001]
---
# 002: 予約APIの実装

## 目的
予約の作成・一覧・キャンセルAPIを実装する

## スコープ
- POST /api/reservations(重複チェック込み。docs/api.md 参照)
- GET /api/reservations?scope=mine
- DELETE /api/reservations/:id(本人のみ)

## スコープ外
- 管理者向けの全予約一覧(003で扱う)

## 受け入れ条件
- [ ] docs/api.md の仕様どおりのステータスコード・レスポンス形式
- [ ] 重複予約が409になる結合テストがある
- [ ] 未認証が401になるテストがある

## 参照
- docs/schema.md, docs/api.md
- knowledge/decisions/2026-07-03-stack.md
```

書き方の要点:
- **受け入れ条件はテスト可能な形で書く。**「ちゃんと動く」は受け入れ条件ではない
- **スコープ外を明記する。** 実装者の善意の拡大解釈が一番の手戻り原因
- 1タスクは実装者の1セッションで完了する粒度に切る(目安: 生成コード数百行以内)

## 完了報告(実装者 → 指示者)

タスクファイルの末尾に追記する:

```markdown
## 完了報告 (2026-07-03)
- 実装: src/app/api/reservations/ 一式、テスト12件(全パス)
- 判断した点: キャンセルは物理削除でなく status=CANCELLED に(履歴が残るため)→ 要承認
- 詰まった点: knowledge/research/2026-07-03-prisma-tz.md に記録
```

指示者はレビューし、「判断した点」を承認したら Decision Record に昇格させるか、
却下して修正タスクを切る。

## 引き継ぎの原則

- セッションをまたぐ情報伝達は **ファイルのみ**。「前のセッションで言った」は存在しない
- 新しいセッションの開始手順は knowledge-management.md の「セッションの始め方」に従う
- 実装者はどのAIツールでもよい。タスク指示書がツール非依存の共通言語になる
