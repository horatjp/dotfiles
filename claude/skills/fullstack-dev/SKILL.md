# フルスタック開発スキル(複数AI協働)

要件から動くシステムまでを、複数のAIセッションをまたいで一貫した品質で組み立てるワークフロー。

前提としている開発形態:
- **1回のセッションでは完成しない。** 別のAI(別セッション・別ツール)が引き継ぐ
- **指示者と実装者を分ける。** 設計・判断・レビューをする側と、コードを書く側は別のAIでよい
- したがって「会話の中にしかない情報」は存在しないのと同じ。判断・設計・学びはすべてファイルに残す

## ワークフロー全体像

```
0. ナレッジ確認 → 1. 要件整理 → 2. スタック・デプロイ先選定 → 3. 設計 → 4. 実装 → 5. テスト → 6. デプロイ
```

自分がいまどの役割(指示者/実装者)で、どのフェーズにいるかを最初に確認する。
役割分担の詳細は `references/multi-ai-workflow.md` を読む。

**スケール調整**: 設計判断を伴わない軽微な修正(単一レイヤーのバグ修正など)では、
フェーズ0(ナレッジ確認)だけ行い、該当フェーズの規約に従って作業する。
ワークフロー全体を最初からやり直さない。

## 0. ナレッジ確認(毎セッション最初に必ず)

`references/knowledge-management.md` に従ってプロジェクトの `knowledge/` を運用する
(基本ルールは project-knowledge スキルが正。判断の記録先は `docs/pdr/` の有無で変わる —
同ファイルの境界ルール参照)。

- **既存プロジェクト**: `knowledge/mistakes.md` → Decision Record → `docs/` の順に読んでから作業する。過去の判断を無自覚に覆さないため
- **新規プロジェクト**: `knowledge/` を作成する
- 以降の全フェーズで、迷って選んだ判断は Decision Record に、ハマった問題は research/ に記録。セッション終了時は `knowledge/daily/` に引き継ぎメモを残す

## 1. 要件整理(指示者の仕事)

コードを書く前に `docs/requirements.md` に短くまとめる:

- **何を管理するか**(主要エンティティ)
- **誰が使うか**(利用者。ロール分離(管理者/一般など)が必要かはここで判断する — 必須ではない)
- **主要ユースケース**(5個前後。CRUD以上のビジネスロジックを含むものを優先)
- **非機能要件**(想定規模、認証の要否、外部連携、**デプロイ先の希望・制約**)

依頼が曖昧なら確認する。ただし質問攻めにせず、妥当なデフォルトを置いて
「この前提で進めます」と宣言して進めてよい。

## 2. スタック・デプロイ先選定(指示者の仕事)

`references/stack-selection.md` を読む。**デプロイ先(VPS / クラウド / Vercel / Cloudflare 等)を
スタックと同時に決める** — デプロイ先の制約がスタック選定を左右するため(特にCloudflare)。
迷ったら Next.js + TypeScript + Prisma + PostgreSQL をデフォルトにする。

選定結果は `docs/requirements.md` に1〜2行で書き、選定理由は Decision Record として記録する
(スタック・デプロイ先は迷わなかった場合でも必須。記録先は knowledge-management.md の境界ルールに従う)。

## 3. 設計(指示者の仕事)

**DB設計を先に、API設計をその後に。** `references/design.md` を読んでから着手する。成果物:

- `docs/schema.md` — エンティティ定義とリレーション
- `docs/api.md` — エンドポイント一覧(パス、メソッド、リクエスト/レスポンス概形、認可要件)
- `docs/rbac.md` — ロール×操作マトリクス(**ロール分離がある場合のみ**)

設計はユーザーに一度見せて合意を取ってから実装に進む。小規模(エンティティ3個以下)なら
設計と実装をまとめて進めてよい。

## 4. 実装(実装者の仕事)

`references/implementation.md`(規約・構成・認証)を読んでから実装する。
管理画面を持つシステムなら `references/admin-user-patterns.md` も読む。

実装順序は依存の向きに従う:

1. スキーマ + マイグレーション + シード
2. 認証基盤(必要な場合)+ ルート保護
3. APIエンドポイント(コアのユースケースから)
4. 画面(APIが動いてから)

各段階で動作確認してから次へ進む。「全部書いてから一気に動かす」は避ける —
問題の切り分けができなくなる。

## 5. テスト(実装者が書き、指示者が確認)

`references/test-deploy.md` のテスト方針に従う。最低限:

- ビジネスロジックのユニットテスト
- 主要APIの結合テスト(正常系 + 未認証401 + バリデーション400。ロール分離があるなら越権403も必須)

網羅よりも「壊れたらすぐ気づける主要経路のカバー」を優先する。

## 6. デプロイ

`references/test-deploy.md` のデプロイ節を読む。VPS / クラウド / Vercel / Cloudflare
それぞれの手順と注意点がある。最低限 `.env.example` と README(セットアップ手順)を必ず用意する。
