# 複数エージェントの動かし方(監督の仕事と起動プロンプト)

2026-10-08作成。2026-10-01〜10-08 の ai-watch の運用(全体レビューと改善10件の並行実装、Haiku 5.5 の測定)で、実際にうまくいったことと詰まったことから組み立てた。

## 1. 監督が実際にやること

今週の記録を数えると、監督の時間の大半は「作る」ことではなく、次の9つに使われていた。

| # | 仕事 | 具体例(今週) |
|---|---|---|
| 1 | 分ける | 改善10件を2系統に分けた。ファイルが重ならない順番(Codex: 1→2→3→7→9、Sonnet: 6→5→8→10→4)を決め、STATUS.md は1人だけが触るようにした |
| 2 | 組ませる | 作る人と見る人の会社を分けた(Sol の作業は Fable、Sonnet の作業は Astra が見る) |
| 3 | 依頼文を書く | 範囲・禁止事項(有料・本番・コミット禁止)・完了条件・報告の形(集計行)を毎回書いた |
| 4 | 起こす | 止まったエージェントに声をかけた。受信箱を見ずに待っていたことが10回以上あった |
| 5 | 決める | 選択肢から決めた(例: lock を変えずに :latest だけ作り直す A案)。決めきれないものはユーザーに上げた |
| 6 | 門番をする | 次の4つを確かめてからコミットした。レビューの集計が P1/P2=0 か。テストが通るか。差分が範囲内か。混ざった差分を分けたか |
| 7 | 有料の実行 | 承認範囲を確かめ、別ペインで実行し、見張り、止まったら原因を調べた |
| 8 | 報告する | 専門用語を外して、ユーザーに結果・判断・待っていることを伝えた |
| 9 | 片付ける | 自動承認を止め、ペインを閉じ、メモリと STATUS を更新した |

### 監督がやってはいけないこと

- **自分で実装する。** 門番が甘くなる。1行の修正でも、実装したら誰かに見せる。
- **黙って選ぶ。** 解釈が分かれるものは、根拠と戻し方を添えて決める。有料・個人設定・アカウントはユーザーに上げる。
- **エージェントの報告をそのまま信じる。** 今週、それで誤った例がある。「0270は本文を見て初めて分かった誤り」という報告は誤りで、抜粋に書いてあった。数字と根拠は自分で1つは確かめる。
- **常に動かすエージェントを増やしすぎる。** 4〜5体で回すと、止まり・取り違え・待ちが増える。常に動かすのは3体まで。

## 3. 起動プロンプト

`<…>` は埋める。どのプロンプトも、最初に agmsg のチームへ参加させる。

### 3.1 実装(Codex Sol)

```
agmsgのスキルで、チーム <team> に <impl-name> として参加してください。
受信箱は、知らせを受けたときに1回だけ確認すること。確認を繰り返すループはしない。

あなたは実装担当です。依頼は bench-cc から agmsg で届きます。
- 1件ずつ実装し、終わったら次の3つをする。
  - bench-cc に報告する(変更したファイル、テスト結果、未確認の点)
  - <reviewer-name> にレビューを頼む
  - 指摘が来たら直し、同じ相手に再確認を頼む
- やらないこと:
  - git commit / push / reset
  - 有料の実行、モデル・APIの呼び出し、本番処理の実行(<禁止コマンドを列挙>)
- 担当外のファイル(<共有ファイル>)は触らない。必要なら bench-cc に頼む。
- 分からないことは推測で埋めない。「未確認」と書いて報告する。
- 完了の条件:
  - テスト(<コマンド>)が通る
  - 差分チェック(git diff --check)が通る
  - レビューの集計が P1=0 P2=0 になる
```

### 3.2 レビュー(Sol の作業は Sonnet・重いときは Fable、Claude の作業は Astra・重いときは Astra xhigh)

```
agmsgのスキルで、チーム <team> に <reviewer-name> として参加してください。受信箱は知らせを受けたときに1回だけ確認すること。

あなたはレビュー担当です。<impl-name> からの依頼で、まだコミットされていない差分を読み、テストを回してください。
コードは変えないこと。指摘を返すだけにする。

見る順番:
1. 結論や数字を誤らせないか
2. お金や安全の境目を越えないか
3. 失敗したときに黙って成功扱いにならないか
4. 既存の記録や互換性を壊さないか
5. テストが本当に弱点を突いているか

指摘の書き方:
- 重さは P1 / P2 / P3。根拠はファイル:行。直し方の案を添える。
- できれば、再現する小さな例を実際に動かして示す。
- 推測の指摘は「要確認」と明記する。

返す先:
- 指摘は <impl-name> へ送る。
- 集計は bench-cc へ1行で送る:「集計: P1=n P2=n P3=n 対象=<#番号> 種類=初回|再確認」

再確認の0件は「新しい指摘なし」という意味。初回の件数を消すものではない。
```

### 3.3 見回り(Haiku 5.5)

```
あなたは見回り担当です。判断や実装はしません。

5分おきに、次のペイン <pane-id 一覧> の画面を `herdr agent read` で読み、次の状態を探してください。
- (a) 入力待ちで止まっていて、受信箱に未読がある
- (b) 確認画面(Press enter to confirm)のまま止まっている
- (c) 15分以上、出力が変わっていない

見つけたら、次のように動くこと。
- (a) のときは、そのペインに「受信箱を1回確認して、届いている依頼を進めてください。」と送る。
- (b) と (c) のときは、自分では押さず、bench-cc に agmsg で「<pane> が <状態> で止まっている」と1行で知らせる。

確認画面で Enter を押してはいけない。有料・コミット・削除の操作が混ざるため。
```

### 3.4 再現テスト係(Sonnet、試行中)

```
あなたはテスト担当です。実装はしません。

<機能の説明>について、実装の前に次のテストを書いてください。
- 満たすべき条件
- 壊れ方の例(境界の値、失敗が成功に化ける経路、壊れた入力、二重実行)

置き場所は <test file>。今は失敗するテストでかまわない。なぜ失敗するべきかを、テスト名とコメントに書くこと。
終わったら、bench-cc と <impl-name> に agmsg で知らせる。実装担当は、このテストを通すことを完了条件にする。
```

### 3.5 事実確認(Sonnet。書き手が Claude なら Codex Sol)

```
あなたは事実確認担当です。<対象>について、次の項目を一次資料(公式ドキュメント・公式ブログ・料金表・CHANGELOG)で確かめてください。
<確かめる項目: モデルID / 料金(段階があるか) / 対応するCLIの版 / 提供範囲>

- 項目ごとに、出典URLと確認日を付ける。
- 二次資料(ブログ・ニュース)しかない項目は「未確認(二次資料のみ)」と書く。
- 推測で埋めない。確かめられない項目が出たら、そこで止めて報告する。
- 結果は bench-cc に送る。
```

### 3.6 週1回の全体監査(Fable xhigh と Astra xhigh)

`reports/review-YYYY-MM-DD/BRIEF.md` に依頼を書き(2026-10-07 の BRIEF.md をひな形にする)、2人に次を送る。

```

reports/review-<date>/BRIEF.md を読み、その手順どおりにプロジェクト全体をレビューしてください。

1. 最初は相手のファイルを読まず、独立に書く。
2. 書き終えたら、相手と賛否を最大3往復までやり取りする。
3. review-fable が joint.md にまとめる。

やってよいのは読むことだけ。コード・データの変更、有料の実行、コミットはしない。
```

## 4. 監督の進め方(1サイクル)

1. **計画を書く。** reports/…/PLAN.md に、項目・担当・順番・触るファイル・レビュー担当・禁止事項を書いて、コミットする。
2. **起動する。**
   - ペインは右側にまとめる。
   - Codex の確認画面の自動承認は、危ない操作(有料・本番・コミット・削除・kill)で止まるようにして動かす。
   - 見回りを置く。
3. **依頼を送る。** agmsg で送ったあと、`herdr agent prompt` で「受信箱を1回確認して」と声をかける。
4. **知らせを待つ。** 受信箱の見張り(Monitor)を張る。30分で切れたら張り直す。届いた集計は insights/review_log.jsonl に記録する。
5. **門番をする。**
   - レビューの集計が P1/P2=0 であることを確かめる。
   - テストが通ることを確かめる。
   - 差分が範囲内であることを確かめる。
   - 混ざった差分はハンク単位で分ける。
   - 関心ごとにコミットする。
6. **有料の実行をする。** 承認範囲を確かめて別ペインで走らせ、終了を見張る。結果はコミットする。
7. **報告する。** 判断、数字、待っていることを、専門用語なしで伝える。
8. **片付ける。** 自動承認と見張りを止め、ペインを閉じる。STATUS とメモリを更新する。

## 5. 今週の失敗から決めたこと

- **受信箱の通知だけに頼らない。** 送ったあとは必ず声をかける。見回りを置く。
- **長い処理はエージェントの道具の時間制限から切り離す。** 例: 再採点は nohup と監督プロセスで動かす。終わったら自動で報告させる。
- **承認ファイルを実装者に書かせない。** 自動判定にも止められる。中身を確かめたうえで監督が置く。照合が厳密なので、中身は書き換えない。
- **同じファイルを2系統が触るときは、コミットの順番を先に決める。** ハンク単位で分けるのは手間がかかる。
- **xhigh は週の枠を大きく減らす。** 今週、Codex の枠が残り19%まで減った。10/5〜10/11の集計では、Astra xhigh の全体レビュー1回で週の枠の約24%、Sol medium の実装5回で計約27%を使った(insights/agent_usage.py。全作業の記録を時刻順に並べ、増えた分を直後に記録したセッションに割り当てた目安)。重いレビューは必要な場面に限り、使う前にダッシュボードの「Codex の週の利用枠」の1行で残りを見る。
- **有料の実行の前に、使うものを実物で確かめる。** 2026-10-11、道具の再確認で zsh の `$c:latest` の `:l` が修飾子になり、新しいイメージに名前が付かず古い版のまま3回走った($0.43が無駄)。シェルの変数は `${c}` と囲み、実行の前に `docker run --rm --entrypoint <cli> <image> --version` などで版を確かめる。zsh の展開の詰まりは2回目。
- **監督の目視をレビューの代わりにしない。** 見逃し台帳(insights/missed_log.jsonl)の最初の3件(P1、2コミット)のうち2件は、コミット文に「監督が確認」とだけあり、レビューの記録がない1つの変更(88526a16)から出た(10/1に入り、10/7の全体監査で見つかるまで6日)。レビューは必ず別のレビュー役に回し、review_log に記録する。review_log の「1回あたりの指摘数」はレビュー役と作業した側が重なっていて交絡しているので、レビュー役の優劣の根拠には使わない(10/11の相談)。
- **同じ差分を2者に独立してレビューさせる(試行中、2026-10-11から)。** 実装の初回レビューは、いつものレビュー役と、もう1者(Claude 側なら Opus か Haiku。Codex 系は重い変更だけ。週の枠を使うため)に同じ差分・同じ指示で頼む。互いの答えは見せない。review_log には同じ target の文字列で、両方「初回」として記録する。監督は2つを突き合わせ、「両方が指摘・片方だけ・誤り」の件数を note に書く。件数の多さでなく、片方だけが見つけた本物の指摘を見る。20組たまるまで集計は見ない(組の数は `python3 insights/review_log.py reviewers` の「同じ作業を2者がレビューした組」のうち初回のもの)。難しい変更だけに偏らせない。
- **後で見つかったP1/P2は見逃し台帳に1行足す。** 監査・点検・障害で見つかったら、入れたコミットを git log と blame で探す。作業した側・当時の初回レビュー役・見つかるまでの日数を insights/missed_log.jsonl に書く。見逃しに数えるのは、当時の仕様と差分から見つけられたもの(discoverable=yes)だけ。見つけられたか分からないものは unknown にする。
- **作業ごとの報告に、声をかけた回数を1行書く。** herdr の `agent prompt` は記録に残らないので、止まりやすさが数えられない(reports/work-2026-10-11/direction/burden.md)。監督自身の作業も、修正したら再確認を記録する。
- **同じ差分を2者にレビューさせている間は、両方の結果が返るまで差分を触らない。** 先に返った指摘を直すと、あとから見る側は直し後の版を見ることになり、同じ差分の組として比べられなくなる。例: 2026-10-12、監督が Sonnet の指摘を先に直したため、Haiku は直し後の版を見た。同じ差分の組として不完全になった(review_log の note。reports/work-2026-10-12/ops.md)。
- **エージェントの状態の見張りは、サンドボックスの外で動かす。** 見張りの Monitor の中からは herdr のソケットに届かなかった(10/12 のこの環境で観測した。reports/work-2026-10-12/ops.md)。例: 2026-10-12、監督の見張り(Monitor)の中から herdr に接続するとサンドボックスで拒まれた(Operation not permitted)。サンドボックスの外のループで `herdr pane list` の agent_status の変化をサンドボックスの内と外で同じパスになる固定のファイル(/tmp/claude で始まる場所など(サンドボックスの書き込み許可の範囲))に書き、Monitor はそのファイルを tail -F する。$TMPDIR はサンドボックスの内と外で違い、最初に $TMPDIR に書いたら Monitor が読めなかった(同じく 10/12 の観測)。blocked(確認画面)になったら監督がすぐ中身を読み、今の依頼で許された範囲の読み取りで、秘密・有料/API・本番処理・ネットワーク取得などの禁止事項に当たらず、コマンド全体を確かめられたときだけ許可する。範囲外や判断できないものはユーザーに上げる。ユーザーから「Codexが止まってます。常に手伝って」と言われた(Codex が ps の確認画面で止まっていた)。
- **作業ごとの報告の「声をかけた回数」は、止まりへの声かけと確認画面の許可を分けて書く。** 例: 10/12 は、止まりへの声かけ2回(review-sol が依頼を受けたまま止まった)・確認画面の許可2回(review-sol、どちらも ps の読み取り)(監督の観測。reports/work-2026-10-12/ops.md)。

## 6. プロジェクトを始めるときの1プロンプト

監督に貼るだけで始められるように、役割とモデルの対応を冒頭の表1か所にまとめた。本文は役割名(監督・実装・レビュー…)だけで書いてあるので、Claude Code・Codex の中でモデルを替えるときは表だけ直せばよい。Pi を入れるとき(いまは未採用)は表だけでは足りず、7章の費用・起動・連絡・終了の手順も依頼文に組み込む。「別系統」とは、提供元(会社)が違うモデルのこと。

```
# 依頼
<作りたいもの・目的・完了の形を2〜5行で>

# チーム(モデルを替えるときはこの表だけ直す)
| 役割 | モデル | 系統 |
|---|---|---|
| 監督(あなた) | <Claude Opus 5.5 medium> | A |
| 実装 | <Codex GPT-6.1 Sol medium> | B |
| レビュー | <Claude Sonnet 5.5 medium> | A |
| 重いレビュー(必要なときだけ) | <Claude Fable 5.1 xhigh> | A |
| 見回り(3体以上を長く動かすとき) | <Claude Haiku 5.5> | A |
常に動かすのは監督・実装・レビューの3体まで。ほかは必要なときに起動して、終わったら閉じる。

# 道具: ペインは herdr、連絡は agmsg
- チーム名: <project>。各エージェントは、agmsgのスキルで役割名(例: impl, review)としてチームに参加させる。
- ペイン(herdr):
  - 起動は `herdr pane split <id> --direction right|down --cwd <repo> --no-focus` → `herdr pane rename <id> "<project>:<役割>"` → `herdr pane run <id> "<CLIの起動コマンド>"` の順。
  - あなたのペインは上下に分けない。ほかのペインは右側にまとめる。
  - 有料の実行は専用のペインで行う。
- 依頼の送り方(agmsg):
  - 本文は一時ファイルに書いて `send.sh <team> <自分> <相手> "$(cat file)"` で送る。シェルの展開事故を避けるため。
  - 送ったあと、`herdr agent prompt <id> "受信箱を1回確認して、依頼を進めて"` で声をかける。
- 受け取り: あなたは agmsg の watch を Monitor で張って、届いた知らせに反応する。30分で切れたら張り直す。
- 様子を見る: `herdr agent read <id>` で画面を読む。確認画面を自動で承認する場合は、有料・本番・コミット・削除・kill の操作では止まるようにしておく。
- 片付け: `herdr pane close <id>` でペインを閉じ、見張りと自動承認を止める。
- 注意: herdrのソケットやDockerは、サンドボックスの中から見えないことがある。その操作だけサンドボックスの外で行う。
```

## 7. Pi を使うとき(2026-10-15 追記)

dotfiles で管理している Pi 1.2.0 とその設定・拡張(この構成では OpenRouter だけを使う)を、チームの3つ目のエージェントにするときの決まり。
根拠は dotfiles 側で Pi を3体動かした試し(sandbox、2026-10-15)。

**いまの運用(ユーザー決定 2026-10-15)**: チームの役にはまだ使わない。使うときは役割と金額をその都度ユーザーに決めてもらう。監督は Claude Code のまま(Pi には Monitor が無く、受信の見張りと確認画面への即応ができない)。Pi に監督をさせる運用はやめる。

### 使うときの決まり

1. **モデルを固定し、系統は提供元で書く。**
   - `openrouter/auto`・`pareto-code`・`fusion`・`free` などの自動振り分けは使わない。試しでは1セッションでモデルが27回替わり、答えた提供元が毎回違った。これでは「実装とレビューは別系統」が守れない。
   - `--model openrouter/z-ai/glm-5.3` のように固定する。固定モデルの既定は GLM 5.3(Z.ai)(ユーザー決定 2026-10-15)。
   - チーム表の「系統」には OpenRouter ではなく提供元(Z.ai・Google・DeepSeek など)を書く。OpenRouter 経由の Claude(`anthropic/...`)は Claude Code と同じ系統 A。
2. **有料の実行として扱う。**
   - Claude Code・Codex の定額枠と違い、1回ごとに OpenRouter のクレジットを使う。起動の前に、使ってよい金額の上限をユーザーに決めてもらう(その都度)。残高は Pi の画面の下に出る。
   - 同時に動かす Pi はまず2体まで。長い作業では区切りごとに `/compact` を指示する。
   - `402 in_flight_budget_exhausted` が出たら、同時に動いている Pi を減らし、`Retry-After`(試しでは120秒)だけ待つ。続けて出るならユーザーにクレジットの追加を相談する。
     試しでは残高 約$78〜80 あっても、3体同時・会話約17.6万トークンで3回止まった(OpenRouter は要求ごとに最大の料金を先に押さえる)。`/compact` で5.4万トークンに減らすと動いた。
   - `openrouter/auto` と `openrouter/pareto-code` は扱える長さが 2M 扱いで自動圧縮が掛からなかった。dotfiles 側でこの2つの上限を 128K に下げてあり、約11万トークンで自動圧縮が掛かる(固定モデルでの閾値は未確認)。
3. **起動と連絡の違い。**
   - agmsg の受信は Pi の拡張が受け持ち、受け取り方は `monitor` だけ(ターンごとに見る方式は無い)。参加や切り替えは次のターンが終わってから効く。
   - 手順は 参加(join)→ 受け取り方を `monitor` にする → `herdr agent prompt` で「受信箱を1回確認して」と声をかけて1ターン回す、の順。
   - 依頼文の中でスキルを呼ぶときは `/skill:agmsg`(Claude・Codex の `/agmsg` とは違う)。
   - 片付けは Ctrl+C では終わらない。`/quit` を送る。
4. **見張り。**
   - Pi も危ないコマンドの前に確認ダイアログを出して止まる。Codex と同じく確認画面も見張る。
   - herdr の `pane list` は Pi のペインも `agent: "pi"` と状態つきで出す。確認ダイアログの間に agent_status が blocked になるかは**未確認**(最初の運用で確かめて、この節に1行足す)。
5. **向く役割。** 依頼を受けて返す役(実装・レビュー・事実確認)。実装やレビューの出来は未確認なので、使うなら小さく試してから。参考: 名前を伏せた比較(blind/challenger_history.jsonl、2026-10-13)では、OpenRouter 経由の GLM・Kimi K3・Qwen の絵(2題×3モデル、計54組)は、Sol 6.1 が選ばれた組32・他社モデルが選ばれた組0・判定が割れた組18・比較できなかった組4。絵の比較なので、コードの実装やレビューの出来を示すものではない。
