# RULES — docs/ai/ 書き込みルール

`docs/ai/` に書き込む前にこのファイルを読むこと。

## 書き込みルーティング

「後で書く」はしない。会話中に都度書き込む。

| 何が起きたか | 書き先 |
|---|---|
| 方針・技術選定・設計・制約を決めた | `decisions/` |
| 技術を調査・比較した | `research/`(調査テンプレート) |
| バグ・問題を解決した | `research/`(バグ解決テンプレート) |
| 参照したURL・仕様書・外部資料 | `references/` |
| 失敗から学びを得た(下記ゲート通過時) | `learnings.md` |
| 作業の区切り・セッション終了 | `STATUS.md` を更新 |

「調査して採用を決めた」場合は両方に書く(research/ に調査結果、decisions/ に決定)。

## 命名規則

- `decisions/`: `YYYY-MM-DD-topic.md`(例: `2026-07-04-database-choice.md`)
- `research/`: `topic-subtopic.md`(例: `auth-token-expiry-bug.md`)
- `references/`: `kebab-case-title.md`(例: `stripe-api-docs.md`)

## decisions/ フォーマット

```markdown
---
date: YYYY-MM-DD
impact: high | medium | low
status: active | superseded
superseded_by:   # superseded のとき必須。置き換えた決定のファイル名
tags: []
related: []   # docs/ai/ からの相対パス
---

# <決定の一言>

## 背景
## 選択肢と比較
## 決定と理由
## 影響・再検討の条件
```

- `impact: high` = アーキテクチャ・技術選定・インフラ構成など影響の大きい決定。
  「選択肢と比較」「影響・再検討の条件」は必須
- `medium` / `low` では「選択肢と比較」「影響・再検討の条件」は省略可
- 新規作成時は `status: active`
- **既存の決定を覆す・修正する決定を書いたAIは、その場で旧ファイルの
  `status` を `superseded` にし、`superseded_by` に新ファイル名を記入する。**
  「後でまとめて」はしない。`superseded` の決定は経緯の参照用であり、
  現在のルールとして扱わない

## research/ フォーマット

技術調査:

```markdown
---
date: YYYY-MM-DD
tags: []
related: []
---

# <ライブラリ/技術名>: <調査テーマ>

## 調査背景
なぜ調べたか(1〜2行)

## 比較・評価
| 選択肢 | 長所 | 短所 |
|---|---|---|

## 結論
採用した/しなかった結論と理由

## 参考
- URL (why_saved: ...)
```

バグ解決:

```markdown
---
date: YYYY-MM-DD
tags: [bug]
related: []
---

# <コンポーネント>: <症状の一言>

## 症状
再現手順・エラーメッセージ

## 原因
根本原因

## 修正
具体的な対処(コードスニペット可)

## 再発防止
次回このパターンに気づくためのシグナル
```

## references/ フォーマット

```markdown
---
date: YYYY-MM-DD
why_saved: <なぜ保存したか1行>
last_checked: YYYY-MM-DD
---

# <タイトル>

URL: <url>

<必要なら要約や引用>
```

## learnings.md 追記ゲート

以下3問に**すべて「はい」**のときのみ追記する。
ユーザーからの訂正だけでなく、AI自身が失敗を分析した結果も対象。

1. 失敗の根本原因を特定できたか(表面的な現象だけなら「いいえ」)
2. 同じパターンが再発し得るか(一度きりの偶発は「いいえ」)
3. 「する/しない」で次回の行動を明記できるか(曖昧な反省は「いいえ」)

形式:

```markdown
## YYYY-MM-DD: <一言で何を間違えたか>
**Signal**: このミスが起きそうな状況・トリガー
**Root Cause**: なぜ起きたか(自分のどういう動き方が招いたか)
**Prevention**: 次回から具体的に何をする/しない
```

## STATUS.md の更新

- タイミング: セッション終了時、または大きな区切り(機能完成・方針転換)
- 常に「今」だけを書く。過去の経緯は decisions/ と git に任せる
- 「次の一手」は、次のセッションがそのまま着手できる具体度で書く

## 棚卸し(ユーザーに「棚卸しして」と言われたときの手順)

1. `decisions/` を走査し、次の2種類を洗い出す
   - `status: superseded` のファイル
   - 「影響・再検討の条件」が現状で成立している `active` なファイル
2. 前者はアーカイブ候補、後者は再検討候補として一覧で提案する(まだ動かさない)
3. ユーザーが承認したものだけを処理する
   - アーカイブ候補 → `archive/YYYY-MM/decisions/` へ移動し、INDEX.md を更新
   - 再検討候補 → ユーザーと再検討し、結果を新しい decision として記録
4. あわせて `learnings.md` も見直し、現状に合わなくなった Prevention があれば
   修正・削除を提案する

## その他の運用ルール

- **INDEX.md の保守**: ファイルの追加・移動・アーカイブをしたAIが即時更新する
- **アーカイブ**: ユーザーの指示(棚卸しを含む)があったときのみ
  `archive/YYYY-MM/` へ退避する。勝手に削除・アーカイブしない
- **報告**: 書き込みは個別に報告する(「`docs/ai/research/xxx.md` に書き込みました」)。
  読み込みはまとめて1行で報告する
- **文体**: シンプルに。装飾・冗長な説明を省く。既存ファイルの形式に合わせる
- **プロジェクト横断の知見**(他プロジェクトでも使える知識)は `docs/ai/` に書かず、
  保存先をユーザーに確認する
