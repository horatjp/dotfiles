# 第4案: 画像カンプ案(作り方と、選ばれた後のHTML化)

HTMLの2〜3案に加える第4の提案枠。Webサイトのデザインそのものを画像として生成する(生成手段がない環境では、そのための記入済みプロンプトが第4案の成果物になる)。画像モデルはWebデザインの視覚資料を大量に学習しており、HTMLを直接書くルートでは出てこない構図・配色・密度感を持ち込める——骨格ロールとは別系統の収束防止エントロピー源。素材写真の生成(SKILL.md手順6のティア2)とは目的が別。

## 環境ごとの分岐

- **生成手段がある場合**(画像生成MCPツール、画像生成対応の外部エージェントへの依頼手段がある): プロンプトへ翻訳して2〜3枚を1回でまとめて生成させ、良い1枚を第4案として成果物に含める。この段階ではHTML化しない
- **生成手段がない場合**(実行AI単体で画像生成できないなど): 記入済みプロンプトを`image-prompt-<第4案名>.txt`として成果物に添え、「画像生成AI(ChatGPT・Gemini等)で生成し、良い1枚をアップロードしてもらえれば第4案として並べます」と案内する
- **合流**: ユーザーがデザインカンプ画像を持ち込んだら(生成の経緯を問わず)、第4案として提示に加える
- **選ばれた後**: ユーザーが第4案を選んだら、手順9の最初に「カンプからの抽出」→HTML化を行う

## 第4案の位置づけ

- HTMLの2〜3案は従来どおり作る。第4案はそれらと**並べて比較する視覚探索枠**であり、HTML案の代替ではない
- 第4案にも仮説(戦略・骨格・トークン・シグネチャー・固有名)を先に立て、ロール・接続テスト・分離ルールを適用する。仮説なしの生成は「きれいだが誰のためでもない」カンプになる
- 生成は2〜3枚を1回の依頼でまとめて頼み(1枚ずつ依頼しない)、良い1枚を第4案に選ぶ

## プロンプトテンプレート

プロンプトは**日本語で**書く——ユーザーが読んで直せることを優先し、勝手に英訳しない(モデルの都合でどうしても英語が必要な場合のみ、日本語の下に英訳を併記する)。

```
縦長のWebサイトデザインカンプを1枚の画像として描いてください
(トップページ全体、ファーストビューから下層セクションまで縦に連続)。

- 題材: {業種と会社の性格を1行}
- 戦略: {仮説の戦略1行}
- ページ骨格: {ロールの骨格を平文で。例: 冒頭に目次を置き、各章へ飛ぶ構成}
- ファーストビュー: {ヒーロー型を平文で}
- トーン: 紙は{明/中/暗}({hex}系)、アクセントは{暖/寒/無彩}({hex}系)、
  見出しは{明朝系/幾何学的サンセリフ/極太ディスプレイ}の性格
- 制約: {制約カードを平文で。例: 角丸を使わず、区切りは細い罫線のみ}
- シグネチャー: {この案が記憶に残る一点を具体的に}
- 文字はダミーでよい(読めなくてよい)。文字の正確さより、
  レイアウト・余白・タイポグラフィの骨格を優先
- ヒーローの見出しは1〜3行に収まる短さで。ファーストビューは要素を絞り、余白を広く
- 意味のない小さなバッジ・ピル・疑似システムラベルを散らさない。カードの中にカードを重ねる入れ子構造にしない
- 写真が入る場所はそれらしい色面・イメージで示す。人物の顔ははっきり描かない
- 実在のWebサイト・ブランドの模倣はしない。透かし・ブラウザ枠は入れない
- 縦長(目安 9:16〜2:3)、フラットなデザインカンプとして。
  {枚数}枚、互いに構図を変えて
```

## 第4案の反復(気に入るまで何度でも)

第4案は画像のまま反復できる。1回で当てにいかない:

- **バリエーション**: 同じプロンプトのまま再生成する(構図違いが欲しいだけのとき)
- **調整**: ユーザーの感想をプロンプトの該当行に反映して再生成する。全文を書き直さず、**変更した行だけを示してから**再依頼すると往復が速い(例: 「トーン: 紙は明→中に変更」)
- **骨格替え**: 方向ごと変えたいときは、別の出目でロールし直して新しいプロンプトを作る(接続テストは毎回行う)
- 生成手段がない環境では、修正版プロンプトを`image-prompt-<案名>-v2.txt`のように版を分けて出力し、外部生成→持ち込みで回す
- 生成物は`comp-<案名>-v1.png`のように版を分けて保存し、上書きしない(「前のと見比べたい」に即応えるため——HTML案のバージョニングと同じ理由)
- 3回調整しても寄らない場合は、プロンプトの言い回しではなく仮説・骨格の側を疑う

## 第4案が選ばれたら: カンプからの抽出(手順9の最初に行う)

画像は「起点」であり再現対象ではない。次だけを読み取り、**文字内容は無視する**:

1. 骨格の実際の並び(セクションの順番・比率・縦のリズム)
2. 余白の密度感(詰まっている場所/抜けている場所のコントラスト、セクション間隔の相対感)
3. 色: 主要色を目視でhexに近似してトークン(`:root`)に起こす。罫線・影の色のロジックも見る。コントラストは実装時に`scripts/check_contrast.py`の実測を正とする(画像の色をそのまま信じない)
4. タイポグラフィの階層感(ジャンプ率・ウェイト差)。書体名は画像から特定できないので、性格の近い実在フォントを充てる
5. 部品の様式: ボタンの形状(角丸・塗り/線・主従の差)、カードの枠と影の使い方
6. シグネチャーがどう表現されたか

**クロップ禁止・セクション再生成**: カンプの一部が小さくて読み取れないとき、その部分を切り抜いて(クロップ・ズームして)抽出の根拠にしない——切り抜きは余白・比率・タイポの関係、つまり抽出したいものそれ自体を歪める。代わりに、生成手段がある環境では「同じデザイン言語(パレット・書体のムード・角丸と部品の様式)のまま、このセクションだけを大きく」と明示してそのセクションを新規に再生成し、そこから抽出する。生成手段がない環境では、読み取れた範囲+当スキルの原則で補完する。

## 実装時の優先順位

HTML実装では、画像より当スキルの品質ルールが常に優先される: 玄関化要件(ナビ・更新枠・サイトマップ)、コントラスト実測、接続テスト、レスポンシブ、事実の捏造禁止。画像カンプはこれらを持っていないので、仕事は「画像の再現」ではなく「画像の翻訳+ルールの充足」。

**実装ドリフトの禁止**: よくある失敗は、カンプは良いのにHTML化の過程で常套骨格・均一な余白・汎用の階層に「均して」しまい、コード版が別物の凡庸なページになること。**変えてよいのは、玄関化要件の注入と文字コンテンツ(インベントリの実データ)だけ**。カンプの視覚言語——余白の寛度、タイポのジャンプ率、部品の様式(ボタン・カード・罫線)、セクションのリズム——は保持する。実装の都合で余白を詰めたり、独特なセクションを汎用の行に置き換えたりしない。

抽出したDNAはトークン(`:root`)に起こし、`renewal-<第4案名>.html`として他のHTML案と**同じパイプライン**で作る——カンプ内の写真枠はイメージの模写ではなく手順6の写真ティア(実素材→生成→ストック→FPO)で実写を充て、玄関化・コントラスト実測・手順7の自己批評と棚卸しをすべて通す。ここで、これまでのHTML案づくりの知見が全部効く。生成カンプを`index.html`に添えるのは任意(添える場合は「AI生成の起点イメージ。実装版が正」と注記する)。
