# code-review

## 使用タイミング
builderが実装を完了し、PR作成またはコミット後にverifierとして呼び出される。

## レビュー観点(優先順)

1. **正しさ**: 要求仕様を満たしているか。テストは意味のあるケースを網羅しているか
2. **安全性**: 入力値検証、認証・認可の抜け漏れ、機密情報のハードコードがないか
3. **一貫性**: 既存コードの命名規則・設計パターンから逸脱していないか
4. **保守性**: 他のエンジニア(または別のAIエージェント)が読んで理解できるか
5. **パフォーマンス**: 明らかな非効率(N+1、不要なループ、同期処理でのブロッキングなど)がないか

## 出力フォーマット

```
## 判定: [承認 / 要修正 / 却下]

### 指摘事項
- [severity: critical/major/minor] ファイル:行 — 指摘内容と理由

### 良かった点
- (該当あれば)

### learningsへの追記候補
- (繰り返し起きそうなパターンがあれば。追記は learnings/ に1エントリ1ファイルで)
```

## 過去の学び(learnings/ 参照)
レビュー実行前に必ず `learnings/` 配下を読み、過去に指摘した繰り返しパターンを
先回りしてチェックすること。`kind: rule` のエントリは必読、`kind: tip` は参考程度でよい。
書式は `learnings/README.md` に従う。

## 禁止事項
- レビュー対象のコードを自分で書き換えない(修正はbuilderに差し戻す)
- 「大体良さそう」で承認しない。具体的な指摘がゼロでも良かった点を明記する
