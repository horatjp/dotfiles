# knowledge/ 格納ルール

各AIロールは、このディレクトリ配下の決められたフォルダのみを参照する設計です。
「どのロールがどの情報にアクセスできるか」を、フォルダ分割+運用ルールで管理します。

## ⚠️ 大前提:この仕組みで防げること・防げないこと

`knowledge_sources` やアクセスマップによる参照制限は、最終的には**AIへの指示文**であり、
認証・認可のような強制力のあるアクセス制御ではありません。

- **防げるもの**: 善意の利用者・AIの事故(業務上不要な機密への接触、古い資料の誤参照、
  うっかりの混入)
- **防げないもの**: 悪意ある利用者による持ち出し、巧妙なプロンプトインジェクション

後者を防げるのは、実行サーフェス側の権限設計(下の「実行サーフェスごとの分離ルール」)と、
このリポジトリ自体のアクセス権だけです。この前提で、機密度と置き場所を判断してください。

## フォルダ構成と内容

| フォルダ | 内容例 | 主な参照ロール | 機密度 |
|---|---|---|---|
| `company-profile/` | ミッション・ビジョン・バリュー・事業内容 | ceo-advisor, strategy-advisor | 低(社外にも出せる情報) |
| `management-policy/` | 経営方針、中期計画の方向性 | ceo-advisor, strategy-advisor | 中 |
| `manuals/` | 業務マニュアル、プロジェクト運営フロー | hr-faq, training-trainer | 低〜中 |
| `rules/` | 就業規則、社内ルール | hr-faq | 中(個人情報は含めない) |
| `training-materials/` | 研修資料、オンボーディング資料 | training-trainer, hr-faq | 低 |
| `strategy-data/` | 業界レポート、競合分析、財務データ | strategy-advisor, ceo-advisor | **高** |
| `archive/` | 改定前の規則・旧版資料など、参照させたくない過去資料 | (どのロールも参照しない) | - |

## 実行サーフェスごとの分離ルール(最重要)

フォルダ分割が機密管理として機能するかどうかは、**実行サーフェス側で分離を再現できているか**
で決まります。

- **Claude Projects**: **1ロール = 1 Project** とし、その Project には該当ロールの
  `knowledge_sources` に列挙されたフォルダの中身**だけ**をアップロードする。
  Project にアップロードしたファイルはその Project 内のすべての会話から見えるため、
  `knowledge/` を丸ごとアップロードした時点でアクセスマップは「お願い」に格下げされます
- **Claude Code / API**: ロールごとに読み取り可能なパスを `knowledge_sources` の範囲に
  制限する(作業ディレクトリの分離、権限設定など)

## 運用ルール

1. **各ファイルに frontmatter を必須にする**
   ```yaml
   ---
   title: 就業規則
   updated_at: 2026-07-01
   status: current        # current / draft / archived
   confidentiality: mid   # low / mid / high(フォルダの機密度と矛盾しないこと)
   ---
   ```

2. **古くなった資料は `archive/` へ物理的に移動する**
   「frontmatter を `archived` にするだけ」の運用は、サーフェスによっては除外が効かず
   誤参照の原因になります(改定前の就業規則を参照して誤回答する、など)。
   参照させたくないファイルはフォルダごと分離するのが確実です。

3. **本当に機密性が高いもの(個人情報、契約書実データ、認証情報)は置かない**
   このディレクトリはAIが日常的に読み込む前提の場所です。個人が特定できる顧客・従業員
   データ、契約書原本、APIキー等は絶対に置かないでください。必要な場合は「参照ID」だけを
   書き、実データはアクセス制御された社内システムに置きます。
   例: `詳細は契約管理システムで CONTRACT-2026-0012 を参照(閲覧権限: 管理部)`

4. **strategy-data/ は機密度が高いため、アクセス範囲を特に絞る**
   財務数値や競合の内部情報に近いものが入りやすいフォルダです。このフォルダを参照する
   ロール(ceo-advisor, strategy-advisor)は `escalation_required: true` を必須とし、
   出力を実行・社外提出する前に必ず人間が確認し、`governance/approvals.md` に記録します。

5. **「置かないルール」を仕組みで支える(性善説にしない)**
   運用が続けば「議事録に給与情報が混ざっていた」は必ず起きます。ルールだけに頼らず:
   - `strategy-data/` と `rules/` への追加・変更は Pull Request を必須にし、
     レビュアーを CODEOWNERS で指名する(誰が・いつ・なぜ、が履歴に残る)
   - 秘密情報スキャン(gitleaks 等)と、電話番号・マイナンバー等の単純なPIIパターン
     検査を CI または pre-commit に導入することを推奨
   - それでも混入は起きる前提で、AIが発見した場合の動きを `governance/escalation.md`
     (「ナレッジ内に置いてはいけない情報を発見した場合」)に定めています

## このリポジトリ自体の置き場所

`knowledge/` には機密度「高」の資料(strategy-data)が入るため、リポジトリは
**プライベート必須**です。組織のポリシー上 GitHub 等の外部サービスに置けない資料がある
場合は、`strategy-data/` を git 管理から外し(.gitignore)、別の安全なストレージに置いて
参照IDで繋ぐ構成にしてください。
