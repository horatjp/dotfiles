# STEP 03 画面設計 / STEP 04 プロトタイプ実装

## STEP 03 画面設計(Skeleton レイヤー)

1. 3文書を前提に、主要な画面ごとにワイヤーフレームを**数パターン**作らせる。指示の型:
   > strategy.md・scope.md・structure.md を前提資料として、このサービスの主要な画面のワイヤーフレームを作って見せて。
   > 主要な画面は数パターン出して比較できるようにして。
2. 1枚の比較ボード(`docs/product/boards/wireframes.html`。ブラウザで開ける単一の HTML)に並べる:
   画面ごとに「採用」「別パターン / ボツ案(参考用に残す)」「オーバーレイ / モーダル」の段を作る
3. ユーザーは見比べて選ぶだけ(ゲート)。選んだ案と理由を進捗表に残す。ボツ案も消さない

この段階では見た目を作り込まない(色・装飾は STEP 08)。配置と流れの確認に集中する。

### 品質の基準は言葉で外部に置く

「かっこよく」「いい感じに」は基準が曖昧で、AI が途中で「これくらいでいい」と止まる。
到達基準を外部の権威で示すと、AI が「まだ足りない」と自分で判断して磨き続けられる:

> FWA・Webby Awards・Awwwards を受賞できるクオリティになるまで、自分でブラッシュアップを繰り返して。

(この言い回しは STEP 08 のデザイン精緻化でも使う。ビジュアルでの伝え方はこのスキルの `references/design.md`)

## STEP 04 プロトタイプ実装

### 下地は作らない(使い捨てのプロトタイプ)

プロトタイプは価値を確かめるための使い捨て。技術スタック・DB/API 設計・開発の下地(project-bootstrap)は、
STEP 05 で Go が出てから STEP 06 の最初に作る。価値が確かめられる前に本番の設計を固めない。
技術はプロトタイプを速く回せるものを AI が選んでよい(非エンジニアには一言で理由を伝える)。
ユーザーが最初から本格運用を前提にすると決めたときだけ、先に project-bootstrap を使う。

### Web 版を先に作る

スマホアプリだけを作りたい場合でも、**まず Web 版で作り込み、あとでネイティブアプリに翻訳する**。

| | 1往復の確認 | 流れ |
|---|---|---|
| いきなりネイティブ | 数分〜十数分 | 実装 → ビルド待ち → スマホに入れる → 実機で確認 → 直すたびに最初から |
| **Web 先行(採用)** | 数秒 | Web 版を実装 → ブラウザで即確認(スマホ向けならスマホ幅で)→ 何十往復もここで仕上げる → AI がネイティブ(Swift 等)へ翻訳 |

AI は言語間の翻訳が得意なので、Web で作り込んだ機能とデザインは無駄にならない。

### 指示の型

> strategy.md、scope.md、structure.md と、ワイヤーフレーム(boards/wireframes.html の採用案)を前提資料として、
> まず Web 版のプロトタイプを一気に実装してください。

- 目的は「一通り触れるもの」を作り、STEP 05 で価値を確かめること。本番品質(認証の厳密さ・課金・
  エッジケース網羅)はまだ求めない。ただし秘密情報をコードに書かない、無断で外部に公開しない、は守る
  (STEP 05 の限定配布はこのスキルの `references/validation.md` の段取りで、AI は準備までにして配布はユーザーが行う)
- 完成したら、ユーザーが自分で触れる起動方法(1コマンド・URL)を伝える

## 完了条件

- STEP 03: ワイヤーフレームの採用案をユーザーが選んだ
- STEP 04: ユーザーが Web 版のプロトタイプを自分で触れる状態になった
