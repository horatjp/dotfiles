# STEP 01 コンセプト設計

何を作るかは人間が決める。AI はユーザーの言葉を引き出して整理し、狙う領域かどうかの確認を手伝うだけ。
**AI がコンセプトを考えて決めない。**

## 進め方

1. ユーザーに、作りたいものを部下に話すように自由に話してもらう(音声入力でよい)。
   最低限ほしいのは次の5つ。足りないものだけ1つずつ聞く:
   - 誰の、どんな課題を解決したいか
   - それでできるようになりたいこと(入れたい機能)
   - こだわりたいこと
   - 避けたいこと
   - 一言でいうと何のサービスか
2. `docs/product/concept.md`(ひな形 `assets/concept.md`)に、ユーザーの言葉を残したまま箇条書きで整理する。
   機能は「どのユーザーのどの困りごとに効くか」が分かる粒度にする。足すときは提案として示し、勝手に書き足さない
3. 課題を測れる形にする(下記)
4. 狙う領域の確認(下記)を一緒に行う
5. 「このコンセプトで進めてよいか」を聞き、明示的な確定を得る(ゲート)

## 課題を測れる形にする

「忙しい人の情報収集を楽にしたい」のようなふわっとした課題のまま機能を考えると、作るものは速く綺麗にできても
的を外しやすい。採用する機能を決める前に、課題を測れる問題に言い直す。AI は次を1つずつ聞いて埋めるのを手伝う
(答えはユーザーが出す。分からない項目は「仮説」と書き、STEP 05 で確かめる):

- **誰の** — 具体的にどんな人か。ひとまとめにしてよい人たちか(初めての人と慣れた人を一緒にしていないか)
- **何が** — 今どうしていて、どこで困っているか(時間・手間・お金・失敗)
- **どれくらい** — 頻度と量(例: 週に何回・1回何分・月にいくら)
- **何と比べて** — 今の代替手段と比べて何が足りないか
- **使う前と後で何が変わるか(差分)** — ユーザーの状態がどう変わるか(例:「毎朝30分かけていた情報収集が5分になる」)。
  機能の一覧ではなく、この差分がコンセプトの芯になる。STEP 05 の価値検証と STEP 11 の成功の指標もここから決める

課題そのものがまだぼんやりしていて掘り下げが要るとき(誰の困りごとか絞れない、課題の候補が複数ある)は、
problem-setting スキルが使える環境ならそれを併用してよい。その課題定義書の問題文・差分を concept.md の上の項目に写す。

## 狙う領域の 2×2 — 「既存AIでは不便」×「すでに払っている」

AI が裏で動くサービスは、使われるほど原価がかかる。完全無料は成り立たないので、
ユーザーが成果に見合うお金を払ってくれる領域を狙う必要がある。

|  | 汎用AIツールで十分 | 汎用AIツールでは不便 |
|---|---|---|
| **すでにお金を払っている** | 汎用AIで充足している | **狙うべき領域**: 不便が残り、財布はすでに開いている |
| **払っていない** | 勝負にならない | 不便は埋まるが、財布は動かない(「便利だね」で終わる) |

- 「汎用AIでは不便」の例: ChatGPT 等で一応できるが毎回やるのは大変 / 手順が多い / 必要なデータ連携ができない /
  記録が残らない・積み上がらない
- 「すでに払っている」の例: 同じ課題を解くために、人の手間(外注・専門家・代行・秘書)や既存のサービス・道具に
  すでにお金を払っている。時間を買う行為(移動・家事・調べものの代行)への支出も含む
- 判定が「財布が動かない」「勝負にならない」になったら、その旨を根拠とともに伝え、ターゲットや課題を
  ずらす案を示す。進めるかどうかは人間が決める(趣味として作るのも自由)

## 始め方(エージェントを使い始めたばかりの人へ)

始め方を聞かれたら、準備は3つだけと伝える:

1. Claude Code か Codex を入れる
2. 空のフォルダを1つ作って開く(そこがエージェントの仕事場になる)
3. 作りたいものを日本語で伝える(音声入力で、部下に話すように: 誰のどんな課題か・やりたいこと・こだわり・避けたいこと)

いきなり大きなものを作る前に、自分の小さな困りごとを1つ作ってみると、作れる感覚がつかめる。

## 完了条件

- `docs/product/concept.md` の5項目・課題の定義(差分を含む)・狙う領域の判定が埋まっている
- ユーザーがコンセプトを明示的に確定した(進捗表の「人間の判断」に日付と要旨)
