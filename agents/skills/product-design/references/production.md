# STEP 06 本番実装

価値検証を通ったプロトタイプを、リリースできる品質に作り込む。実装は AI に任せてよいが、
**実装した AI とは別系統の AI にレビューとテストをさせる**ことが要点。

## 1. 下地をつくる(project-bootstrap)

STEP 05 の Go を受けて、ここで初めて本番の技術スタック・デプロイ先・DB/API 設計と開発の下地を決める。

**先にプロトタイプの扱いを決める(ゲート)。** STEP 04 のコードは `docs/product/` と同じフォルダにあり、project-bootstrap の
下地はプロジェクト直下に展開される。呼ぶ前に、AI が次を比較と推奨付きで提案し、ユーザーが決める(開放質問にしない。
`prototype/` などへの退避や別リポジトリ化を、ユーザーに聞かずに既定にしない):

- 配置 — 同じリポジトリでプロトタイプを退避する(例: `prototype/` や別ブランチ)か、別リポジトリにするか
- 引き継ぐ部分 — 画面・ロジック・スタックのうち本番に持ち込むもの
- 作り直す部分 — 本番の設計(認証・課金・データ)で新しく作るもの
- STEP 05 で本物のデータ用に前倒しで作った部分と、預かっているデータ — 引き継ぐか、作り直すか、消すか
  (参加者への説明と食い違わないように)

決めた内容は進捗表の「人間の判断」に残す。

そのうえで project-bootstrap に `docs/product/` の concept・strategy・scope・structure・validation と、プロトタイプの場所と
上の決定を渡し、決まったことは聞き直さないよう伝える。引き継ぎ(`docs/STATUS.md` の次の一手)に
「initial-build の完了後は `docs/product/README.md` の STEP 06 の続き(レビュー・テスト)へ戻る」と書かせる。
以後のコードの変更は、そのプロジェクトの AGENTS.md と changes/ の進め方に従う。

## 2. ネイティブアプリへの翻訳(対象がスマホアプリのとき)

**先に前提を案内する。** 対象のプラットフォームが決まった時点で、実機での確認 / テスト配布 / ストアでの公開のそれぞれに
何が要るか(開発者アカウントの登録、必要な機材と開発環境、費用、審査の有無と所要)を、その時点の公式情報で確認して
ユーザーに案内する。登録や準備はユーザーが行い、時間がかかるものは早めに始めてもらう(具体的な費用・日数はここに
書かない。その時点で確かめる)。

STEP 04 で Web 版を作り込んだのは、ここでネイティブへ翻訳するため。Web 版の機能とデザイン(STEP 08 を先に
進めているならデザインシステムも)を前提資料に、AI にネイティブのコード(例: iOS なら Swift)へ翻訳させる。
ビルドと実機での確認はユーザーが行う(手順は AI が1ステップずつ案内する)。
ストアへの申請は外部への送信。リリース前チェック(`references/launch.md`)の後に、AI は申請の中身と手順をそろえて止まり、申請はユーザーが行う。

## 3. 役割分担

| 役割 | すること |
|---|---|
| 人間(ユーザー) | 重い実装(課金・認証・データ移行など)は AI に仕様を考えさせてから Go / NoGo を判断する。根深いバグの方針を選ぶ |
| 監督 | 全体の計画・監督・全量レビュー。実装役を並列に動かして取りまとめる |
| 実装 | 実装(並列に分けてよい) |
| 独立レビュー・QA | **実装役と別系統(提供元が違う)の AI** がコードレビュー・テスト・バグ探しを行う |

系統によって得意が違う(ある系統は発想とデザインが得意、別の系統はコードが厳密でバグをよく見つける、など)。
タイプの違う人同士でレビューするのと同じ構造にする。

**チームの組み方と配役(どのモデルが何をするか)は multi-agent-kickoff スキルのチーム表に従う。**
このスキルが決めるのは「実装役とレビュー役は別系統」「重い実装は人間が Go / NoGo」の2つの原則だけ。

別の AI を起動できない環境では、下のレビュー指示書をユーザーに別の AI へ渡してもらう。それもできないときは、
未レビューのまま進むかをユーザーに聞き、了承を日付付きで進捗表に残す。

**コードを別系統の AI に見せる前に** — 共有する対象(ブランチ / ディレクトリ)と除外する対象(`.env` などの環境ファイル・
鍵ファイル・顧客データ・判断ページに貼ったスクリーンショット)を指示書に明記し、秘密の値を表示・転記せずに、
共有対象に含まれていないことを確認する。

### レビューの記録と完了

レビューの記録は `docs/product/reviews.md`(ひな形 `assets/reviews.md`)。指摘ごとに
**方針**(対応する / 意図した設計として記録 / 見送り(理由))と**状態**(未着手 / 修正済み / 再確認済み)を分けて書く。

- 「対応する」にした high の指摘は、修正 → 検証 → 独立した再確認(レビュー役が修正を見る)まで終えて「再確認済み」にする。
  方針を決めただけ、修正しただけでは完了にしない。既存のテストシナリオ表の合格は、新しく見つかった不具合の修正の証拠にならない
- high の指摘を見送るときは、AI が理由を書いて閉じるのではなく、ユーザーの明示的な判断(日付)を残し、
  残るリスクをリリース前チェックへ渡す

### レビュー指示書の型

```
あなたは独立レビュアーです。実装者とは別の視点で、厳しくレビューしてください。
対象: <変更の範囲・ブランチ>(共有しないもの: 環境ファイル・鍵・顧客データ)
前提資料: docs/product/strategy.md・scope.md・structure.md
観点: 仕様との不一致 / バグ / エッジケース / エラー処理 / セキュリティ / テストの抜け
報告: 指摘ごとに 重大度(high/medium/low)・該当箇所・再現手順・修正案
修正はしないでください。
```

## 4. 重い機能も AI に検証させる

課金・決済のように失敗が許されない機能も、実装からテストまで AI に進めさせる。
ブラウザや PC を操作できる AI に、決済フローを通しで検証させる(「指示書とチェックリスト」を作らせ →
実行させ → 「実行結果」を報告させる)。安全のため:

- 決済サービスの**テスト(サンドボックス)モード**のキーとアカウント、テスト用カード番号だけを使う(キーの発行と
  サンドボックスの用意はユーザーが行う)。これは SKILL.md「全工程で守ること」の例外(開発中の API 呼び出し: 開発用の
  キー・サンドボックスに限り、接続先の確認と費用の上限の範囲で AI が呼んでよい)の範囲。本番モードの設定・商品作成・
  公開は外部操作なので AI は準備までで止まり、ユーザーが実行する
- AI に管理画面のパスワードを渡さない。ログインはユーザーが行い、本番モードの画面を AI に操作させない
- AI に操作させるブラウザは専用のプロファイル(他のサービスにログインしていないもの)にする
- 最後の確認は人間が行う

## 5. 根深いバグは人間が関与する

同じバグが繰り返す・直すと別の所が壊れる、と感じたら、AI に表面的な修正を続けさせない。次の定型プロンプトで止める
(ユーザーにも、すぐ呼び出せるようスニペット登録を勧める):

> 以下の問題の根本原因を分析して、根本解決方法を分かりやすく提案してください。まだ実装はしないで下さい。

AI は原因と解決案(複数なら比較)を非エンジニアにも分かる言葉で説明し、ユーザーが方針を選んでから実装する。

## 6. 「もぐらたたき」はテストシナリオ表で抜け出す

チャット型など入力が無限通りある AI サービスは、網羅的なデバッグができない。代わりに:

1. 「ユーザーはこの範囲で使うはず」というテストシナリオ表を AI に作らせる
   (`docs/product/test-scenarios.csv`、ひな形 `assets/test-scenarios.csv`。数百件になってよい。ひな形の例行 S1 は
   作成時に置き換える)。正常系だけでなく、曖昧な入力・想定外の話題・上限到達・連続操作・悪意のある入力も入れる。
   優先度の P0 は「落ちたらリリースしない」ケースに付ける
2. **実行する前に**、接続先を確かめる(DB は使い捨てのコピー、外部サービスは検証用、本番の鍵は未設定。
   SKILL.md「全工程で守ること」)。AI の API を呼ぶのは同項の例外(開発用のキーに限り、接続先の確認と、最初にユーザーが
   決めた費用の上限の範囲)の中で。外部へ送信・公開する操作はテストに含めない(含めるなら、その部分はユーザーが実行する)
3. 全件を AI に実行させ、結果列を埋めさせる。判定が決定的でないもの(AI の応答の質)は
   「AI判定」として合格基準を言葉で書き、別の AI に判定させる(これも上限の中で)
4. 失敗したシナリオを直し、表を回帰テストとして使い続ける(画面やプロンプトを変えたら再実行する)

AI を使うサービスでは必須の工程。

## 完了条件

- scope.md の Phase 1 機能が実装され(対象ならネイティブへの翻訳も)、別系統の AI のレビューを受けている。
  reviews.md で「対応する」にした high の指摘がすべて「再確認済み」で、見送った high にはユーザーの判断(日付)がある。
  別系統のレビューを受けられなかった場合は、ユーザーの了承が日付付きで残っている
- テストシナリオ表の P0 が全件合格
- 重い機能(課金・認証)の検証結果がある
