# STEP 09 セキュリティチェック

自分で作ったものに脆弱性がないかは、リリース前に必ず確かめる。最善はシニアのセキュリティエンジニアの
レビューだが、その前に AI で必ずできることとして **ペネトレーションテスト**(攻撃者の立場で実際に攻撃を
試し、通ったところを塞ぐ検査)を行う。

## 始める前に

1. **秘密情報の確認** — コード・リポジトリ・クライアント(配布物)に API キー等が含まれていないかを先に確認する
   (値を表示・転記せず、含まれていないことだけを記録する)
2. **接続先の確認と隔離** — 攻撃を実行する環境の接続先を確かめる: DB は使い捨てのコピー、外部サービス(決済・メール・
   AI・分析)は検証用の接続先、本番の鍵は未設定。確認できない項目があれば止めてユーザーに聞く。
   攻撃は本番環境・他者のサービス・外部 API を対象にしない
3. **AI の API を呼ぶ試験の上限** — AI 連携の試験(プロンプトの保護・利用料の濫用)は AI の API を繰り返し呼ぶ。
   SKILL.md「全工程で守ること」の例外(開発用のキーに限り、接続先の確認と、最初にユーザーが決めた費用の上限の範囲)の
   中で始め、上限に当たったら止める。外部へ送信・公開する操作(本番や他者のサービスへの送信)は試験に含めない
4. **別系統の AI へのコードの送信は人間が行う** — AI は共有対象・除外対象・指示書をそろえて止まり、送る操作はユーザーが行う

## 構成 — 領域を分けて、別系統の AI と突き合わせる

1. **領域ごとに担当を分ける**(並列にできる環境ではサブエージェントを並列に。できない環境では領域ごとに順に行う)。
   プロダクトの構成に合わせて領域を決める。例:
   | 領域 | 主な観点 |
   |---|---|
   | Web アプリ | 認証・認可、ユーザー間のデータの分離、入力検証、インジェクション |
   | スマホアプリ | 鍵・トークンの保管、通信の保護 |
   | ブラウザ拡張 | 要求する権限の最小化、データの送信先 |
   | AI 連携 | プロンプトの保護(プロンプトインジェクション)、AI 利用料の濫用(上限・レート制限) |
   | 課金 | 支払い状態の改ざん、Webhook の検証 |
2. **別系統の AI にも独立に**同じ対象をテストさせる(multi-agent-kickoff。起動できなければ指示書を作って
   ユーザーに渡してもらう)。これは領域分担とは別の要件で、逐次にしても省かない。
   コードを見せる前に、共有する対象(ブランチ / ディレクトリ)と除外する対象(環境ファイル・鍵・顧客データ)を
   指示書に明記し、秘密の値が共有対象に含まれていないことを確認する
3. **監督役が指摘を突き合わせる** — 重要な指摘はコードを開いて裏取りし、誤検知を除く
4. 見つかった穴をリリース前に塞ぎ、塞いだことを再テストで確かめる

記録は `docs/product/security-review.md`(ひな形 `assets/security-review.md`)。指摘だけでなく、**領域ごとの実施記録**
(対象の版・環境、試したこと、実施者、結果と証跡、未実施とその理由)を残す。指摘がゼロの領域も「何を試して
何も通らなかったか」を書く。コードを読む検査と、実際に攻撃を試した検査は分けて書く。
未実施の理由を書いた行は、記録ではあっても検査の合格には数えない。

## 指示の型

> あなたは攻撃者です。<領域> について、このプロダクトにペネトレーションテストをしてください。
> 攻撃手法を考え、ローカルの検証環境(接続先: <確認済みの検証用の接続先>)で実際に試し、試した攻撃の一覧と、
> 成功した攻撃の根拠(該当コード・再現手順)を報告してください。本番環境・他者のサービス・外部 API には
> 攻撃を送らないでください。修正はしないでください。

## 完了条件

- 全領域に実施記録があり、全領域のテストと別系統の AI のテストが終わっている(別系統の AI を使えなかった場合、
  または未実施の領域を残して進む場合は、未検査の範囲を明示してユーザーが日付付きで明示的に了承した)
- high の指摘が全て処置・再テスト済み
- 残したリスクがあれば理由とともに記録し、ユーザーが了承した
