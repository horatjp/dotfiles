# product-design — アイデアからリリースまでの11工程

AI エージェントを使って、外部に公開・販売するプロダクト(Web サービス・スマホアプリ・ブラウザ拡張・CLI ツール・
AI を使う課金サービス)をアイデアからリリースまで作り切るための進め方。
AI に作らせ、**人間は選んで決める**。工程の多くは AI に任せられるが、次の4つは人間にしかできない:

1. **コンセプトの言語化** — 何を、誰のために作るか
2. **価値の判定** — 自分(一番のユーザー)が毎日使うか、なくなったら困るか
3. **価格の決定**
4. **重要な仕様の意思決定** — 体験・原価・セキュリティ・課金に効く分岐

4つはどれも「何を解くか」を決める仕事。AI は「どう解くか」を速くするが、解く問題を誤ると、その速さで
間違った場所に着く。だから重要でない問題を完璧に作るより、重要な問題を選び直すほうを優先する。
この4つの場面では、AI は案と根拠を示して**必ず止まり**、ユーザーの明示的な決定を待つ(ゲート)。
「いいね」などの相槌は決定として扱わない。

## 0. 前提確認(毎回最初に)

### このスキルで進めるかの確認

依頼が project-bootstrap(社内向けシステムの計画と下地作り)とどちらにも読めるとき(例:「Webアプリを作りたい」
「B2B の SaaS を作りたい」)は、1問だけ確認する: 「外部のユーザーに出して、価値の検証や価格まで自分で決めて
リリースするプロダクトですか? それとも、決まった要件のシステムを計画どおりに作りたいですか?」
前者ならこのスキル、後者なら project-bootstrap。

### 作業場所と進捗の確認

1. **作業場所** — 作業ディレクトリがこのプロダクト専用のフォルダか確かめる。ホームや無関係なリポジトリなら、
   新しい空のフォルダを作って開き直すよう提案する(始め方を聞かれたら `references/concept.md` の「始め方」)
2. **全工程か、工程1つだけか** — 先にここで分岐する
   - **既存のプロダクトで工程を1つだけ頼まれた**(例: 価格設計だけ、リリース前のペネトレーションテストだけ)→
     その工程の reference を読んで、その工程から始める。扱う成果物はその工程に要るものだけ。前の工程の成果物が要る
     (例: 価格設計に scope.md が要る)なら、既存のコードや資料から読み取って要点だけ確認する。進捗表はまだ作らない。
     その工程が終わったら、進捗表を作って11工程で続けるかをユーザーに聞き、続けるなら次の 3 へ
   - **全工程で進める** → 次の 3 へ
3. **進捗表** — `docs/product/README.md` を読む
   - **ある** → 表の「状態」と「次にやること」から再開する。成果物ファイルと食い違っていれば、ファイルの実態に
     合わせて表を直す。ゲートの決定は推測で埋めない(記録がなければユーザーに確認する)
   - **ない** → `docs/product/` を作り、このスキルの `assets/README.md` をコピーして進捗表にする。
     作りかけのもの(コード・企画書)があれば読んで、済んでいそうな工程を示し、ユーザーに確認してから表を埋める
4. **再開のしかたを毎回伝える** — ゲートで止まるときとセッションの終わりには、次に再開するときの決まり文句を
   ユーザーに伝える(新しいセッションがこのスキルを自動で読むとは限らないため)
   - 全工程で進めている → 進捗表を最新にしたうえで「`docs/product/README.md` を読んで、product-design の続きを進めて」
   - 工程1つだけ(進捗表なし)→ 扱った成果物のパス・工程名・次の一手を添えて「product-design の STEP NN を
     `docs/product/<成果物>` の続きから進めて」。このためだけに進捗表を作らない

### 記録の置き場(どれが正か)

- **`docs/product/` が、プロダクトの「何を・なぜ」(コンセプト〜構造・価値検証・価格・デザイン)の正**。
  進捗表 `docs/product/README.md` には状態と、ゲートの決定の1行要旨(日付)だけを書き、詳細は各成果物に書く
- セッションをまたぐ情報はファイルだけ。会話で決めたことは必ずファイルに残す
- 導入先に project-template の構成(`docs/decisions/_template.md`)があるときは、そのプロジェクトの AGENTS.md が優先する:
  - `docs/STATUS.md` の現在地には「product-design STEP NN(`docs/product/README.md` 参照)」とだけ書く
  - ゲートの決定のうち、後から覆すと影響が大きいもの(コンセプト・価格・重要な仕様)は `docs/decisions/` にも残す
  - `docs/requirements.md` は project-bootstrap / project-template の正典として残し、冒頭で `docs/product/` を前提資料として参照させる
  - コードの変更は、そのプロジェクトの changes/ の進め方に従う(本番実装は project-bootstrap が作る `changes/initial-build/` から)

### 使う人に合わせる

最初のやり取りで、ユーザーがエンジニアかどうかを推し量る(分からなければ一度だけ聞く)。

- **非エンジニア** — 専門用語には一言の説明を添える。技術的な判断(スタック・構成・テスト方法)は AI が推奨案を出して
  要点だけ確認する。ユーザーの時間は4つのゲートとビジュアルでの選択に使ってもらう
- **エンジニア** — 説明は最小限にし、技術的な選択肢はトレードオフ付きで示して任せる

## 11工程

各工程に入ったら、対応する reference を読んでから着手する(全部を先に読まない)。
成果物は導入先の `docs/product/` に置く(ひな形はこのスキルの `assets/`)。判断用の HTML・ワイヤーフレーム・
ムードボードは `docs/product/boards/` に置く。

| # | 工程 | AI がやること | 人間が決めること(ゲート) | 成果物 | 読む reference |
|---|---|---|---|---|---|
| 01 | コンセプト設計 | 言葉の整理、狙う領域の判定の手伝い | **コンセプトの確定** | concept.md | `references/concept.md` |
| 02 | 仕様設計 | UX 5レイヤーの Strategy → Scope → Structure を1層ずつ文書化 | **各層の確定・重要な仕様の分岐** | strategy.md・scope.md・structure.md | `references/ux-5-layers.md` |
| 03 | 画面設計 | 主要画面のワイヤーフレームを数パターン | 採用案を選ぶ | boards/wireframes.html | `references/screens-and-prototype.md` |
| 04 | プロトタイプ実装 | 使い捨ての Web 版を一気に実装 | (触って確かめる) | コード | `references/screens-and-prototype.md` |
| 05 | 価値検証 | 限定配布の段取りと集計 | **Go / 改善 / 撤退**(他の人の本物のデータを預かるときは、その前にも) | validation.md | `references/validation.md` |
| 06 | 本番実装 | 下地づくり(project-bootstrap)、ネイティブへの翻訳、実装、**別系統の AI によるレビュー・テスト** | 重い実装の Go / NoGo、根深いバグの方針 | コード・test-scenarios.csv・reviews.md | `references/production.md` |
| 07 | 価格設計 | 原価の実測(開発用のキー・費用の上限内)、利用者分布を仮定したシミュレーション | **価格の決定** | pricing.md | `references/pricing.md` |
| 08 | デザイン精緻化 | ムードボード → デザインシステム → 全画面、判断ページ | デザインシステムの確定、案の選択 | design-system.md・boards/ | `references/design.md` |
| 09 | セキュリティチェック | 領域分担のペネトレーションテストと別 AI との突き合わせ | 残すリスクの了承 | security-review.md | `references/security.md` |
| 10 | マーケティング素材 | LP・ストア画像・紹介動画・プレスリリース | 公開前の確認 | launch.md | `references/launch.md` |
| 11 | 計測設計 | イベント設計、タグのコードと設定内容・手順の準備 | **外部ツールへの反映の実行** | launch.md | `references/launch.md` |
| → | リリース | 公開前チェックリストと公開手順の準備 | **公開の判断と実行** | launch.md | `references/launch.md` |

### 順番について

- 下の工程が上の工程の前提になる(例: 仕様が決まる前に画面を作らない、価値検証の前に本番実装しない)。
  順番を飛ばしたい依頼には、飛ばすと何が起きるかを伝えてから、ユーザーの判断に従う。飛ばした工程は進捗表に「省略(理由)」と書く
- 戻るのは普通のこと(価値検証で刺さらなければ STEP 02〜04 に戻る)。戻ったら進捗表の状態も戻す
- 07(価格)と 08(デザイン)は本番実装と並行してよい。ただし 07 の原価の実測は対象の機能が動いてから。
  07 で決めたプラン・利用上限・上限到達時の体験は scope.md に反映し、実装との差分があれば STEP 06 に戻して
  実装・境界値のテスト・独立レビューを行う。08 で画面を作り直したら、テストシナリオ表を再実行する。
  09〜11 とリリース前チェックはすべてリリース前に終える

## 隣接スキルとの受け渡し

| 場面 | 使うスキル | 渡すもの |
|---|---|---|
| STEP 05 で Go が出た後、STEP 06 の前に開発の下地(AGENTS.md・docs/・changes/、技術スタック、DB/API 設計)を作る | project-bootstrap | `docs/product/` の concept・strategy・scope・structure・validation と、プロトタイプの場所と扱い(`references/production.md` の「1. 下地をつくる」でユーザーが決めた配置・引き継ぐ部分・作り直す部分)。決まったことは聞き直さないこと、引き継ぎ(`docs/STATUS.md` の次の一手)に「initial-build の完了後は `docs/product/README.md` の STEP 06 の続き(レビュー・テスト)へ戻る」と書くことを伝える |
| STEP 06・09 で、実装役と別系統の AI にレビュー・テストさせる | multi-agent-kickoff | 役割の原則と、レビュー役の指示書(`references/production.md`・`references/security.md` の型)。配役(どのモデルが何をするか)は multi-agent-kickoff のチーム表に従う |
| STEP 10 の紹介動画 | video-production | コンセプト・訴求点・画面素材 |
| STEP 10 の LP を単体の静的サイトとして作る | web-page-builder | デザインシステム・コピー |

STEP 04 のプロトタイプは下地なしで作る(価値が確かめられる前に本番の設計を固めない)。
ただし、ユーザーが最初から本格運用を前提にすると決めたときは、STEP 04 の前に project-bootstrap を使ってよい。

## 全工程で守ること

- **外部への送信・公開・課金は、AI は準備までで止まり、実行は人間が行う** — 限定ベータの配布、アンケートフォームの
  公開・送付、ストア申請、決済サービスでの設定、分析ツール側の設定、計測タグの設置(検証環境も本番も)、
  プレスリリースの配信、本番デプロイ、別系統の AI へのコードの送信のすべてで、AI は準備(手順・中身・送信先・費用)を
  そろえて示し、止まる。実行はユーザーが行い、結果を AI に伝える。「確認を取れば AI が実行してよい」とは読まない。
  **例外(開発中の API 呼び出し)**: 開発用のキー・決済のサンドボックスに限り、接続先の確認(下の項目)と費用の上限
  (最初にユーザーが決める)を満たす範囲で、テスト・原価の実測・決済テストのために AI が API を呼んでよい。
  公開・配布・送信・外部ツールの設定は、この例外に含まれず、引き続き人間が実行する
- **秘密情報を書かない** — API キー・トークン・パスワードはコード・文書・判断ページに書かず、環境変数で渡す。
  AI に管理画面のパスワードを渡させない。記録に残すのは鍵の用途と識別名だけで、値は書かない
- **検証・攻撃を実行する前に接続先を確かめる** — テストシナリオ表の全件実行やペネトレーションテストのように、
  AI が実際に操作・攻撃を実行する前に、接続先を確認する: DB は使い捨てのコピー、外部サービス(決済・メール・AI・
  分析)は検証用の接続先、本番の鍵は未設定。確認できない項目があれば止めてユーザーに聞く。攻撃は本番環境・
  他者のサービス・外部 API を対象にしない。原価の実測(STEP 07)のように実際の API が要る作業は、ユーザーが
  許可した開発用の接続先で、下の上限の中で行う
- **有料 API を繰り返し呼ぶ前に上限を決める** — テスト表の全件実行・AI 判定・ペネトレーションテスト・原価の実測など、
  AI の API を繰り返し呼ぶ作業(上の例外の範囲)は、使うキー(ユーザーが用意した開発用のもの。本番の鍵は不可)と
  費用の上限・止める条件を最初にユーザーに決めてもらってから始める。上限に当たったら止めて報告する。
  鍵の発行・予算の設定はユーザーが行う
- **分析・調査を AI に頼むときは問いを渡す** — 「このデータを分析して」ではなく、目的・分解の軸・比較対象を添える
  (例:「継続が落ちた原因を知りたい。登録月ごと・利用開始からの週ごとに分けて、前の月と比べて」)。
  解決策に飛びつく前に、定義する → 分解する → 比較する → 仮説を立てる → 数字で確かめる、の順で進める
- **判断はビジュアルで** — 細かい選択肢が並ぶときは、テキストで聞かずに判断用の使い捨て HTML を作る
  (`references/design.md` の「判断ページ」)
- **品質の基準は外部に置く** — 「かっこよく」ではなく「FWA・Webby Awards・Awwwards を受賞できる水準まで」のように、
  AI が「まだ足りない」と自分で判断できる基準で指示する
- **ツール名は例** — 文中のツール・モデル名は執筆時の例。その時点で使えるものに読み替え、役割
  (実装役とは別系統のレビュー役、など)を守る
- **作りたいという意志がいちばんの燃料** — 途中で手が止まったら、次の一手を小さく区切って示す
