# マルチエージェントの起動と監督

監督(このセッション)は原則として自分では実装しない(自分で直してよいのは設定値・記録・文書の小変更だけで、それも別会社の1者に見せてから入れる。playbook §1)。作業を分け、役割ごとのエージェントを herdr のペインで起動し、agmsg で依頼・報告をやり取りする。レビューを通ったものだけを監督がコミットする。

道具は既存のスキルを使う。
- ペインの操作: `herdr` スキル
- エージェント間の連絡: `agmsg` スキル

### herdr-app の中で使うとき(2026-11-03 追記。原本 playbook には未反映)

この文書と playbook のペインの手順は TUI の herdr 用。herdr-app(Herdr.app + herdr-core)の中にいるかどうかは `herdr-app` スキルの「どちらを使うか」で判定する。herdr-app と判定したら:
- ペインの操作は、すべて `herdr-app` スキルの手順に置き換える。開く・並べる(pane.split)、チームへの参加の頼み方、声かけ(`herdr agent prompt`・agmsg の poke の代わりに `hc send`)、画面を読む(peek・`herdr agent read` の代わりに `hc read`)、見張る(ループの代わりに `hc wait`)、片付け(despawn の代わりに pane.close と `hc kill`/`hc rm`)。agmsg の spawn・arrange・peek・poke・despawn は使わない。
- 確認画面(`hc wait` の `blocked`)は `herdr-app` スキルどおり、画面を読んでユーザーに上げる。下の手順4、playbook §4 の Codex の確認画面の自動承認、playbook §5 の「読み取りだけ監督が許可する」は TUI での運用で、herdr-app では使わない。
- 起動プロンプト(playbook §3・§6)は「そのまま使う」のでなく、herdr のコマンド・agmsg の Monitor の張り方・確認画面の自動承認の指示を、`herdr-app` スキルの手順に置き換えて渡す。依頼文に「ペインの操作と確認画面の扱いは herdr-app スキルを優先する」と書き添える。
- 依頼・報告・レビューの集計は agmsg のまま(履歴を残す)。門番(手順5)の決まりも変わらない。
- 有料の実行(手順6)と、費用を自動で見張って上限の前に止める予備環境の運用(playbook §7)は、herdr-app での見張りと停止の手順をまだ確かめていない。確かめるまでは herdr-app では行わず、TUI の herdr で行う。

## 手順

1. **チーム表を決める。** 下の「始めるときの1プロンプト」の表を埋める。モデルを替えるときは、この表だけを直す。
   - 実装した人と、その実装をレビューする人は、**別系統(提供元が違う)**のモデルにする。
   - 常に動かすのは3体(監督・実装・レビュー)まで。重いレビューと見回りは、必要なときだけ起動する。
   - 分ける境目は作業の種類でなく、コンテキストと独立性で決める。少ない入力で完結して小さな結果を返す作業だけを渡し、監督の文脈を長く説明しないとできない作業は範囲を切り直す(playbook §2、2026-10-26)。
2. **計画を書いてユーザーに見せる。** 次の項目を、プロジェクト内のファイル(例: `reports/<日付>/PLAN.md` や `docs/`)に書く。了承を得てから起動する。
   - 項目
   - 担当
   - 順番(触るファイルが重ならないように)
   - 完了条件
   - 禁止事項
3. **起動する。**
   - ペインは右側にまとめる。監督のペインは上下に分けない。
   - 各エージェントは agmsg の役割名でチームに参加させる。頼み方は「`join.sh` で team=<チーム>、name=<名前>、type=<種類>、project=<フォルダ>。そのあと actas <名前>。ほかのチームには登録しない」の形に固定し、参加後に `team.sh <チーム>` で載ったかを確かめる(playbook §5、2026-11-07)。
   - 依頼文は一時ファイルに書いてから送る。送ったら `herdr agent prompt` で「受信箱を1回確認して」と声をかける。
4. **見張る。**
   - 監督は agmsg の watch を見張る。30分で切れたら張り直す。
   - 止まっているエージェントには声をかける。受信箱を見ずに待っていることがよくある。
   - エージェントの状態(止まり・確認画面)は、サンドボックスの外のループで常に見張り、すぐ手伝う。確認画面は、禁止事項に当たらない読み取りだけ許可する(playbook §5)。
   - 3体以上を長く動かすときは、見回り役を置く。
   - 合図は1つ: 監督の受信が agmsgd で直接届くときは、依頼文に `hc send` の「報告した」を書かない。作業役の終わりは新しい報告ファイルの最後の1行(`tail -n 1`)で待ち、`hc wait` の繰り返しで待たない。作業役の依頼文には「権限の確認で止められた操作は、消す・上書きせず、依頼の範囲内で権限確認の理由(ネットワーク・本番・秘密・書き込み先など)や承認要件を回避しない代わりの方法で進めるか、理由や許可範囲が不明なら止まって報告する。監督は代わりに実行しない」を入れる(playbook §4・§5、2026-11-07)。
   - 報告の本文はファイルに書かせ、agmsg には要点とパスだけを送らせる。監督はまず要点と集計の行だけを読み、本文や画面は門番で根拠を確かめるとき・P1/P2 が残るとき・重さを付け直すとき・止まったときに開く(playbook §3.1・§3.2・§4)。
5. **門番をする。** 次の4つがそろった項目だけを、関心ごとに分けてコミットする。レビューの集計は記録に残す。監督が目で見ただけの変更はコミットしない(レビューの記録がない変更から、後で重大な不具合が出た)。
   - レビューの集計が P1=0・P2=0
   - テストが通る
   - 差分が範囲内に収まっている
   - 根拠の数字を1つは自分で確かめた
6. **有料の実行・元に戻せない操作はユーザーの承認を得て、監督が別ペインで行う。** 費用は上限を決めて、超えそうなら止める。
7. **報告して片付ける。**
   - 区切りごとに、結果・判断・ユーザーに決めてほしいことを、専門用語なしで伝える。
   - 終わったら、確認画面の自動承認と見張りを止め、ペインを閉じ、進捗の記録を更新する。
   - 進捗の記録(STATUS・PLAN.md)は、書き込みを許された範囲で節目ごと(依頼・集計・判断や保留・長い待ちの前・項目の終わり)に更新する。会話が自動の要約で縮んでも、記録から続けられるようにするため。ユーザーに `/clear`・`/compact` は頼まない(playbook §4)。

役割ごとの起動プロンプト(実装・レビュー・見回り・再現テスト係・事実確認・週1回の全体監査)、監督の9つの仕事、これまでの失敗から決めたことは [references/playbook.md](references/playbook.md) にある。起動の前に、該当する節を読む。

## 既定のチーム(2026-10-18時点)

この表は決定ではなく、その時点でいちばん良い組み合わせ。ai-watch で新しいモデルの測定・比較・週1回の全体監査のたびに見直す(playbook §2)。

| 役割 | モデル | 系統 |
|---|---|---|
| 監督 | Claude Opus 5.5 medium | A |
| 実装 | Codex GPT-6.1 Sol medium | B |
| レビュー(Sol の作業) | Claude Sonnet 5.5 medium | A |
| レビュー(Claude の作業) | Codex GPT-6.1 Terra medium(混雑で動かないときは Astra medium) | B |
| 重いレビュー(お金・停止条件・測定の結論・保存データ・セキュリティ) | Sol の作業は Claude Fable 5.1 xhigh、Claude の作業は Codex Astra xhigh、さらにもう1者(少なくとも1者は作業した側と別会社) | A / B |
| 見回り | Claude Haiku 5.5 | A |

Opus は主のレビュー役にしない。Luna は使わない(根拠は playbook §2)。

Claude と Codex が使えないときの予備環境は、Pi で OpenRouter を使う(playbook §7)。予備環境では監督も Pi にしてよい。ペインの用意と起動は人が行う。予備環境では、完了の前に境目の入力を作り、期待する結果を先に書いて実行・照合させる(playbook §7、2026-10-20)。

| 役割 | モデル(提供元の固定) | 系統 |
|---|---|---|
| 監督(依頼とまとめだけ) | DeepSeek V4 Pro 0813(alibaba、2番目に deepinfra/fp8) | DeepSeek |
| 実装 | DeepSeek V4.1 Flash 1017(inference-net/fp8) | DeepSeek |
| レビュー(2026-10-28 に Muse から替えた。10/31 の試しで、チームのペインで起動し、初回と再確認の依頼を受けて報告を返した。1回だけ) | MiniMax M3.1 Flash(novita/fp16・medium。models.json に直接書いたモデル。重さと説明は監督が付け直す。予備に Muse Spark 1.3) | MiniMax |
| 重いレビュー(候補・未確認) | Kimi K3(morph/fp8) | Moonshot |

根拠は ai-watch の測定とレビュー記録。
- 検索・集計の課題: Sol 6.1 が首位、Haiku 5.5 は Sonnet 5.5 より上。
- Sonnet のレビュー: Sol の作業から P1 を1件、P2 を9件見つけた。
- Fable のレビュー: Sol の作業から P1 を2件見つけた。
- ただし、レビュー役ごとに見た作業が違うので、件数でレビュー役の優劣は決められない(交絡)。いまの配置は能力の順位を証明したものではない。同じ差分・同じ依頼文を2者に独立して見せた有効な初回の組が20組たまったら見直す(playbook §5)。

Sonnet が実装するときは、レビューを Codex に回す。xhigh は週の利用枠を大きく使うので、必要なときだけ呼ぶ。

Pi(OpenRouter 経由で他社のモデルを動かす)は、Claude と Codex が使える通常のチームでは役に使わない(ユーザー決定 2026-10-15)。上の予備環境を含め、使うときは、モデルの固定・金額の上限・起動と連絡の違いを playbook §7 で確かめてから。
