# 依頼: <件名>のレビュー(<レビュー役>)

あなたはレビュー担当です。ファイルは変えないこと(報告ファイルの作成だけ可)。コミット・push・stash・reset・履歴の書き換えをしない。有料の実行・ネットワーク・API 呼び出しはしない。読むのは差分と、食い違いの確認に要る節だけ。
<試しの実行が要るなら: 一時フォルダで、時間と回数の上限を付けて可>

- <playbook §2 の「権限の決まり」の文をそのまま入れる>
- 仕様の質問で止まらず、計画に無いことは今の動きを保って「未確認」として報告に書く。
- 計画: <計画ファイルのパス>、報告: <作業役の報告ファイルのパス(再確認のときは最新のもの)>
- 対象: <差分の取り方(`git diff` など。新しいファイルがあればその確かめ方)>
- 見る点: 見る順は playbook §5。今回の重点: <…>
- 範囲: <…>。範囲の外の指摘は数えない(秘密・お金・止める条件・壊れた入力を点検させるときは、守る相手 <…>、守らない相手 <…>(理由)、動かす環境 <…> も書く)
- 指摘: P1(直さないと壊れる・危ない)/ P2(直すべき)/ P3(任意)、根拠は ファイル:行、直し方の案。推測は「要確認」

## 返す先
- <報告ディレクトリ>/review-<名前>.md に書く(再確認は review-<名前>-2.md など新しいファイル)。最後の行は飾りなしの `P1=n P2=n P3=n`(再確認は `再確認 P1=n P2=n P3=n`。何回目でも `再確認` と書き、ほかの前置きを付けない)
- 書き終えたら、頼んできた相手に `hc send` の1行で知らせる(止められたら送らない。最後の行の合図が正)
- 再確認の集計は、その版でまだ残っている指摘(直っていない前の指摘+新しい指摘)の数。前の指摘が直ったかを確かめずに0件にしない。初回の件数は記録に残す
