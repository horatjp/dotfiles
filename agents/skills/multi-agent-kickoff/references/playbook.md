# 複数エージェントの動かし方(目的と境界)

2026-11-07 に、固定の手順を減らして目的と守る境界だけに書き直した。旧版の全文を読める git のコミットの案内・日付つきの経過・測定は `<ai-watch>/docs/knowledge/multi-agent-trials.md`(根拠の置き場。ここに新しい決まりは書かない)。Pi の予備環境は `<ai-watch>/docs/knowledge/multi-agent-pi.md`。`<ai-watch>` は ai-watch リポジトリを置いた場所。

## 1. 目的と原則
- 監督は作業を分けて頼み、門番をする。目的は、実装を速く回すことと、間違いを通さないこと(コンテキストを減らすこと自体ではない)。
- 作業とレビューは別系統(提供元が違うモデル)にする。同じ会社どうしを別系統と数えない。
- 常に動かすのは3体(監督・実装・レビュー)まで。重いレビューなどは必要なときだけ起動し、終わったら閉じる。
- 分ける境目は、作業の種類でなくコンテキストと独立性。少ない入力で完結して小さな結果を返せる作業だけ渡し、監督の文脈を長く説明しないとできない作業は範囲を切り直す。
- 監督が自分で直してよいのは設定値・記録・文書の小変更だけで、それも別会社の1者に見せてから入れる(重い変更(§2)はもう1者)。
- 解釈が分かれるものは黙って選ばず、根拠と戻し方を添えて決める。決めきれないものはユーザーに上げる。
- エージェントの報告(数字も、「しなかった」の申告も)をそのまま信じない。数字と根拠は1つは自分で確かめる。分からない・確かめられないことは推測で埋めず、「未確認」と書いて確かめるか止まって聞く。
- 1つのセッションで済む小さな作業には使わない。

## 2. 境界(必ず守る)
- **お金・本番・秘密・アカウント・個人設定・削除など元に戻せない操作は、ユーザーの承認を得てから監督が行う。** 費用は上限を決め、超えそうなら止める(Pi の OpenCode Go は定額なので金額の上限は聞かず、枠の残りで止める。扱いは `<ai-watch>/docs/knowledge/multi-agent-pi.md`)。有料の実行はその専用の端末で行い、終わりと停止(`hc wait`・`hc kill`、TUI は `herdr agent wait` など)を見張る。
- **承認の印は監督が置く。** 承認ファイルなど承認を表す印は、ユーザーの承認を監督が確かめて置く。作業役に作らせたり書き換えさせたりしない。有料の実行の前に、使うものを実物で確かめる。
- **コミット・push・履歴の書き換えは監督だけ。** 作業役・レビュー役はしない。
- **門番:** 次の4つがそろった項目だけを、関心ごとに分けてコミットする。レビューの集計が P1=0・P2=0、テストが通る、差分が範囲内、根拠の数字を1つは自分で確かめた。レビューの記録がない変更、監督が目で見ただけの変更はコミットしない。計画のコミットは、門番を通った変更と一緒にする。
- **レビューは別会社の1者。** お金・停止条件・測定の結論・保存データ・セキュリティに触れる変更は重い変更として、もう1者を付ける。2者に同じ差分・同じ依頼文を見せている間は、両方の結果が返るまで差分を直さない(先に直すと、後から見る側が直し後を見て比べられなくなる)。
- **権限の決まり(作業役・レビュー役の依頼文に、この文をそのまま入れる。原文はここだけ):** 操作が権限の確認で止められたら、消す・上書きする操作を含まず、依頼の範囲内で、権限確認・拒否の理由(ネットワーク・本番・秘密・書き込み先など)や承認の要件を回避しない代わりの方法で同じ結果が得られるかを確かめて進めるか(理由や許可範囲が不明なら進めず報告する)、止まって監督に報告する。監督は止められた操作を代わりに実行しない。代わりの方法でも判断がつかないものはユーザーに上げる。
- **確認画面の許可(TUI・herdr-app 共通):** 今の依頼の範囲の読み取りで、秘密・ネットワーク・有料・本番・書き込み・削除を含まず、コマンド全体を確かめられたものだけ、監督が許可してよい(選ぶ前に、画面全体でカーソルと選択肢を確かめる。経過は trials)。範囲外・判断できない・画面から欠けて確かめられないものはユーザーに上げる。`hc send --force` で確認を飛ばさない。新しいフォルダで Claude を動かすときは、計画の了承を取るときに、そのフォルダの信頼もユーザーに一緒に聞く。了承があれば監督が画面でカーソルと対象のパスを確かめてから選ぶ。了承がなければ押さず、設定ファイルへ信頼を書き込んで飛ばさない。
- **頼まれたことと範囲を守る。** 依頼文の「触るファイル」の外は変えない。レビューの依頼には範囲と、範囲外の指摘は数えないことを先に書く。秘密・お金・止める条件・壊れた入力を点検させるときは、守る相手・守らない相手(理由つき)・動かす環境も書く。
- **ペインの扱い。** 監督のペインは上下に分けず、ほかは右側にまとめる。自分が開いたペインと端末だけを閉じる。ユーザーのほかの作業は触らない。

## 3. チーム(表はここだけ)
決定ではなく、その時点でいちばん良い組み合わせ。新しいモデルの測定・週1回の全体監査のたびに見直す。

| 役割 | モデル | 使う場面 |
|---|---|---|
| 監督 | Claude Opus 5.5 medium | 常に(主のレビュー役にはしない) |
| 実装 | Codex GPT-6.1 Sol medium | 常に |
| レビュー(Sol の作業) | Claude Sonnet 5.5 medium | 常に |
| レビュー(Claude の作業) | Codex GPT-6.1 Terra medium(混雑で動かないときは GPT-6 Astra medium。2026-11-30 までに再比較) | Sonnet・Fable など Claude 側が実装・執筆したとき |
| 2本目の実装 | Claude Sonnet 5.5 medium | 並行させたいとき(手戻りの影響が小さい作業) |
| 重いレビュー | Sol の作業は Claude Fable 5.2 xhigh、Claude の作業は Codex GPT-6 Astra xhigh、さらにもう1者(少なくとも1者は作業した側と別会社) | 重い変更(§2) |
| 再現テスト係・事実確認 | Claude Sonnet 5.5 medium(事実確認は書き手が Claude なら Codex GPT-6.1 Sol) | 仕様が細かい実装の前・新モデルの ID や料金の確認。書き手と別系統 |
| 週1回の全体監査 | Claude Fable 5.2 xhigh + Codex GPT-6 Astra xhigh | 週1回。Codex の週の枠に余裕がある日 |

- Luna は使わない(名前を伏せた比較で絵・文章とも Sol 6.1 に負け、Sol と同じ週の枠を使うので節約にならない)。xhigh は週の枠を大きく使うので、必要なときだけ呼び、使う前に残りを見る。作業の質が足りないときは、試験などで確かめられるかを見る → effort を1段上げる → 上のモデルを低い effort で試す、の順に考える(枠と別系統の決まりは守り、表を変えるのは測定か月1回の見直しのあと)。
- **枠が少ないとき:** 起動の前に Claude の `7d`(ステータスライン)と Codex の `weekly N% left`(画面下)の残りを見る。どちらかが 20% を下回ったら、少ない側はレビューだけに回し、実装は多い側にする(別系統は例外にしない。20% は目安)。両方が下回る・別系統の組が組めないときはユーザーに相談する。残りの少ない側では xhigh を呼ばない。
- **Claude の作業役は外部の道具なしで起動する:** `claude` に `--strict-mcp-config --no-chrome` を付ける。付けないと、監督と同じ Gmail・Drive・カレンダー・ブラウザの操作など MCP の道具(2026-11-11 に数えて9種類・127個)を引き継ぎ、依頼文の禁止だけで外への送信を止めることになる。付けると0個になった(同日、Sonnet のペインで確認)。ブラウザで見た目を確かめる役だけは `--no-chrome` を外す
- 小さく続きものの項目は、実装役が同じペインで続けるのを基本にする。コンテキストが大きくなったときや前と関係のない項目では新しいペインにしてよい。
- モデル名は `data/models.jsonl` の `name` と同じ表記で書く(略称は結び付かない)。
- この表は使うAIのページの入力(`derive`)。行や見出しを変えたら全体の試験を回し、月1回の見直しの記録の役割と合わせる。
- Claude と Codex が使えないとき、またはそれ以外のモデルを入れたいとき: Pi(`<ai-watch>/docs/knowledge/multi-agent-pi.md`)。

## 4. 連絡と見張り
- 依頼は、報告ディレクトリのファイル(`reports/<日付>/req-<名前>.md` など)に書き、`hc send <端末> -- '<ファイル>を読んでその依頼どおりに進めてください'` の1行で知らせる(伝言は `--` を付ける。TUI は `herdr agent prompt`)。ペインどうしも `hc send` で話してよい。
- 依頼を送ったら、状態か画面で届いたことを確かめる(TUI は直後に `idle` のままのことがある。読み方は herdr スキル)。
- Codex の質問は状態が `blocked` で出る。画面に `? 1 question` と出たら `shift+left` で開き、`enter` などで答える(codex-cli 0.167.0 で確認。更新で変わりうる)。
- 監督がエージェントの質問に答えるときは、文頭に「監督の判断です」と書く。エージェントには監督の入力とユーザーの入力の区別がつかないため。報告で「ユーザーの回答」と書かれていたら直させる。
- 報告は報告ファイル(`impl.md`・`review-<名前>.md`)に書かせ、最後の行を飾りなしの合図にする(実装は `実装完了`、レビューは `P1=n P2=n P3=n`、再確認は何回目でも `再確認 P1=n P2=n P3=n`。`最終確認` など別の前置きを付けない)。直した後の報告は新しいファイル(`impl-2.md` など)にする(前の合図に反応しないため)。監督はスキルの `scripts/wait-signal.sh`(使い方・終了コード・相手の状態の読み方はスクリプトの先頭。herdr-app の実機の `blocked` は未確認)かファイルを読んで待つ。待つときは相手(TUI は agent 名、herdr-app は端末)を渡すのを基本にする。
- 再確認の集計は、その版でまだ残っている指摘(直っていない前の指摘+新しい指摘)の数。前の指摘が直ったかを確かめずに0件にしない。初回の件数は記録に残す。
- 再確認を2〜3回しても重い指摘が新しく出続けるときは、直し続ける前に監督が原因を見て、作りを簡単にするか範囲を切り直すかを考える(回数は目安。直すたびに仕組みを足すと、足した所に新しい指摘が出る)。範囲の外にした未解決の指摘は明記し、門番を通ったことにはしない。
- 見張り: 監督は、止まり(`blocked`・`error`)・終わり(`finished`)・ターンが終わったのに報告の合図がない状態・見張り自体の失敗に気づけるようにする。やり方は任せる(状態の読み方・知らせが来ない端末の扱いは herdr-app / herdr スキル)。状態だけでは拾えない確認画面もあるので、必要なら画面全体を読む。見張りの出力は1行の合図に絞り、時間切れ・失敗も1行で知らせる(失敗を「合図なし」や正常と取り違えない)。サンドボックスからソケットに届かない場合も、監督を含め §2 の権限の決まりに従い、許可された方法(通常の確認を通して外で動かすなど)で接続する。判断できなければユーザーに上げる。
- 画面は要るときだけ読む。ふだんは状態、足りなければ末尾の数十行、確認画面や止まりの調査は今の画面全体(コマンドと `--lines` の意味は herdr-app スキル)。TUI は `herdr agent read <id> --source visible`。
- 止まっているエージェントには声をかける。
- 長い処理は道具の時間制限から切り離して動かし、試しや試験には実時間の上限と止める手段を付ける(秒数やコマンドは決めない)。終わったら報告ファイルに書かせる。

## 5. 依頼文に書くこと
役割ごとの定型の文面は持たない。依頼文は短い箇条で、次を書く。ひな形は `references/templates/`(スキルにある)。
- 範囲と目的、作業場所(依頼文の作業場所と実際に起動する場所が合っているかを送る前に確かめる)、読む計画ファイル。触るファイル(これ以外は触らない)と順番(原本を先に、写しを後など)
- やらないこと(commit・push・reset・stash、有料の実行、ネットワークなど)と、§2 の権限の決まりの文
- 聞かずにしてよいこと(読み取り・試験の再実行など、繰り返しても安全なもの)も1行書く。禁止だけを並べると、Fable 5.2 などは日常の作業まで控える([Anthropic の Fable 5.2 向けの書き方](https://platform.claude.com/docs/ja/build-with-claude/prompt-engineering/prompting-claude-fable-5-2)「慎重さが積み重なるのを防ぐ」、2026-11-11 確認)。理由が当てはまらなくなった注意は依頼文・記憶から消す
- 完了条件: テスト・差分チェック・レビューの集計。境目の入力(空・欠け・失敗・壊れた入力・二重実行など)を最初の依頼に並べ、それぞれの試験を完了条件に入れる
- 報告ファイルのパスと最後の行の合図
- 報告は作業の画面やファイルを見ていない読み手に向けて書かせる。結論を最初の数文に置き、作業中に作った呼び名は使わない
- レビューには、見る順(結論や数字を誤らせないか → お金・安全の境目 → 失敗が成功扱いにならないか → 既存の記録・互換性 → テストが弱点を突いているか → 頼まれていない機能・一度しか使わない抽象化・消せる分岐がないか)、重さ(P1 直さないと壊れる・危ない / P2 直すべき / P3 任意)、根拠(ファイル:行)、直し方の案、推測は「要確認」を書く。レビュー役はコードを変えない。再現できるなら小さな例で示す
- 消す・名前を変える・置き場を変える作業は、実装の前に、それを読んでいる・書き出している箇所(コード・試験・文書・ページのリンク)を調べて、一覧を計画に書く
- 成果物をどう起動・利用するか(直接開く・サーバー・ビルド)が分かれるときは、計画の時点でユーザーの言葉から決めて完了条件に書く。

役割ごとに足すこと(1行ずつ):
- **実装:** 1件ずつ実装し、レビューを頼み、指摘を直して再確認を頼む。P1・P2 が0件になったら(初回でも再確認でも)、P3 は直さず監督に返す(直すかは監督が決める。門番が見た版と最終版がずれないため)。担当外のファイルは触らない。
- **レビュー:** 差分とテストを読み、指摘と集計だけ返す。再確認のときは前の指摘が直ったかを確かめる。
- **再現テスト:** 実装の前に、満たすべき条件と壊れ方の例を、今は失敗してよいテストで書く(なぜ失敗するべきかをテスト名とコメントに書く)。実装役はこれを通すことを完了条件にする。
- **事実確認:** 一次資料(公式ドキュメント・料金表・CHANGELOG)で、項目ごとに出典 URL と確認日を付ける。二次資料のみは「未確認(二次資料のみ)」。推測で埋めず、確かめられなければ止めて報告する。
- **週1回の全体監査(Fable と Astra):** `reports/review-YYYY-MM-DD/BRIEF.md` に依頼を書く。最初は相手のファイルを読まず独立に書き、そのあと相手と賛否を最大3往復し、1者が合意案にまとめる。確認項目に「役目が終わって消せるものはないか」を入れる。削除については候補を一覧にするだけにし、消すかはユーザーが決める。読むことだけをする(変更・有料の実行・コミットなし)。

## 6. 記録
- STATUS・PLAN は、書き込みを許された範囲で節目(依頼・集計・判断や保留・長い待ちの前・項目の終わり)に更新する。会話が自動の要約で縮んでも、記録から続けられるようにするため。ユーザーに `/clear`・`/compact` は頼まない。
- チームを1回動かしたら、`<ai-watch>/docs/knowledge/multi-agent-runs.md` の表に振り返りの1行を足す(書き込みを許された範囲のときだけ。範囲外なら書かず報告に1行)。分からない欄は「不明」。5回分たまるか週1回の監査のときに、効いていない決まり・手間や間違いを増やした決まりを外すか簡単にする案を出し、ユーザーに決めてもらう。決まりを足すだけにしない。
- ai-watch のレビュー記録(review_log・見逃し台帳・2者比較の hash・20組の数え方)の実装は ai-watch の `insights/review_log.py` と `insights/missed_log.py`、過去の細かい手順は trials「旧 playbook の全文」の git のコミットの案内から読める。経過は trials「§5 監督の目視をレビューの代わりにしない」「§5 同じ差分を2者にレビューさせている間は」にある。この playbook には書かない。レビューの集計は記録に残し、後で見つかった P1/P2 は見逃し台帳に足す。
- 区切りごとに、結果・判断・ユーザーに決めてほしいことを、専門用語なしで伝える。終わったら見張りを止め、自分が開いたペインを閉じる。

## 7. 予備環境
Claude と Codex が使えないとき、またはそれ以外のモデルを入れたいときは Pi を使う。費用の上限と見張り(OpenRouter は費用の自動の見張り、OpenCode Go は枠の残りを監督が見る)・提供元の固定・承認は境界なので `<ai-watch>/docs/knowledge/multi-agent-pi.md` で確かめてから。
